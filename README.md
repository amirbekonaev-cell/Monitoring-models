# Мониторинг упоминаний компании — MVP

Сервис ищет упоминания компании в интернете, складывает их в базу и показывает на дашборде.

**Статус этапа:** недели 3–4 из плана ТЗ — охват «весь интернет». Работают все пять каналов
сбора (RSS, поисковый API, Telegram, соцсеть VK, универсальный парсер сайта), каждый на своей
BullMQ-задаче с изоляцией ошибок (падение одного источника не останавливает остальные и не
роняет воркер). Администратор добавляет источники сам через UI по ссылке — тип определяется
автоматически. Работают ключевые слова (обязательные/минус-слова/точная фраза, с фолбэком на
ручные словоформы для казахского языка) и дедупликация перепечаток. Тональность, дашборд,
уведомления и роли — на следующих этапах, см. `10. План работ по неделям` в ТЗ.

## Архитектура

- **backend/** — NestJS API + 5 BullMQ-сборщиков (по одному на канал), TypeORM-миграции
- **frontend/** — React + TypeScript: лента упоминаний, раздел «Источники», раздел «Ключевые слова»
- **PostgreSQL** — хранилище (источники, упоминания, ключевые слова), full-text search и pg_trgm
- **Redis** — очередь задач для фоновых сборщиков (BullMQ)

Каждый канал — отдельный BullMQ `JobScheduler` с собственным интервалом. Внутри цикла каждый
источник обрабатывается в своём `try/catch`: при ошибке источник помечается `status = 'error'`
с человекочитаемой причиной в `lastError`, а цикл идёт дальше по остальным источникам (ФТ-2).

## Каналы сбора

| Канал | Реализация | Почему так |
|---|---|---|
| К-1 Поисковый/новостной API | NewsAPI.org `/v2/everything` | бесплатный ключ без модерации, булев синтаксис запроса (`OR`/`NOT`/кавычки) ложится на модель ключевых слов напрямую |
| К-2 RSS | `rss-parser` | без изменений с прошлого этапа |
| К-3 Telegram | скрапинг публичной веб-версии `t.me/s/<channel>` через Cheerio | обычный Bot API требует, чтобы бот был админом канала — не подходит для произвольных публичных каналов по ссылке; MTProto требует авторизации по номеру телефона. Веб-превью отдаёт последние посты без токена и без вступления в канал |
| К-4 Соцсеть | VK API `newsfeed.search` | официальный API, приложение и `access_token` выдаются мгновенно без ручной модерации (в отличие от X/Meta), релевантно для рынка РФ/КЗ |
| К-5 Универсальный парсер | Cheerio: `og:title`/`og:description`, `<article>`, `article:published_time` и другие мета-теги даты | эвристики по ТЗ |

К-1 и К-4 не привязаны к списку ссылок админа — это глобальный поиск по активным ключевым
словам, поэтому под них при первом старте backend автоматически заводится одна системная
запись в `sources` (чтобы у них тоже был видимый статус/последний успешный сбор в UI).

## Как запустить

Требуется Docker Desktop (с Docker Compose).

1. Скопируйте файл с переменными окружения:

   ```sh
   cp .env.example .env
   ```

   По умолчанию там нет реальных секретов — только настройки для локального запуска.
   Для продакшена обязательно замените `DB_PASSWORD` на свой.

2. (Опционально, но нужно для К-1 и К-4) добавьте в `.env`:
   - `NEWSAPI_KEY` — бесплатный ключ на https://newsapi.org/register
   - `VK_ACCESS_TOKEN` — создайте приложение на https://vk.com/apps?act=manage, получите
     токен с правами на чтение новостной ленты

   Без этих ключей каналы К-1/К-4 будут исправно опрашиваться по расписанию, но каждый раз
   получать понятную ошибку («NEWSAPI_KEY не задан…») и оставаться в статусе `error` — это
   штатное поведение ФТ-2, не падение сервиса.

3. Поднимите весь стек одной командой:

   ```sh
   docker compose up --build
   ```

   Это поднимет: PostgreSQL, Redis, одноразовый сервис `migrate` (накатывает миграции и
   добавляет 3 реальных RSS-источника казахстанских новостных сайтов), backend и frontend.

4. Откройте в браузере: **http://localhost:5173**

   - Вкладка «Лента» — упоминания
   - Вкладка «Источники» — список источников (тип/статус/последний успешный сбор/число
     упоминаний) и форма «добавить по ссылке»
   - Вкладка «Ключевые слова» — управление обязательными/минус-словами/точными фразами

5. Логи сборщиков видно в выводе backend-контейнера:

   ```sh
   docker compose logs -f backend
   ```

   Ищите строки `<Канал> cycle start` / `<Канал> cycle done` — видно, сколько источников
   опрошено, сколько материалов найдено/новых/перепечаток/отфильтровано по ключевым словам.

## Источники (US-2)

Список хранится в БД (таблица `sources`), редактируется через UI на вкладке «Источники»:

- **Добавление по ссылке.** Алгоритм автоопределения типа:
  1. ссылка на `t.me/...` или `@channel` → канал К-3 (Telegram);
  2. иначе проверяем, есть ли RSS/Atom-лента — сама ссылка уже валидный фид, либо в её HTML
     есть `<link rel="alternate">`, либо фид лежит по стандартному пути (`/rss`, `/feed`,
     `/rss.xml`, `/feed.xml`, `/atom.xml`) → канал К-2 (RSS);
  3. иначе → канал К-5 (универсальный парсер страницы).

  Сразу после добавления источник опрашивается один раз («тестовый сбор») — админ сразу
  видит либо «нашлось N материалов», либо понятную причину ошибки текстом (не стектрейс).

- **Отключение/удаление.** Источник можно отключить (перестаёт опрашиваться, но остаётся в
  списке) или удалить — ранее собранные упоминания при этом остаются в базе
  (`mentions.source_id` становится `NULL`).

## Ключевые слова (US-3)

Вкладка «Ключевые слова»: обязательные слова, минус-слова, точная фраза в кавычках.

- Правило фильтрации: если активных обязательных/точных ключевых слов нет вообще — фильтр
  выключен, идёт всё подряд (как на прошлом этапе). Если есть — материал должен совпасть
  хотя бы с одним обязательным/точным ключевым словом и не совпасть ни с одним минус-словом.
- **Морфология.** Для русского (`language = ru`, без ручных словоформ) совпадение ищется
  через `to_tsvector('russian', ...) @@ plainto_tsquery('russian', ...)` — учитывает падежи/
  склонения автоматически. Для казахского в Postgres нет готового FTS-словаря, поэтому по
  умолчанию (`language = kk`) используется явный список словоформ (`manual_forms`), заданный
  вручную через запятую в форме добавления — совпадение ищется как обычная подстрока по
  каждой форме. Это же ручное поле можно включить и для русских ключевых слов, если
  автоматическая морфология не устраивает.
- Изменение списка применяется только к следующему циклу сбора: каждый цикл сборщика один
  раз загружает снимок активных ключевых слов и использует его до конца цикла — уже
  собранные упоминания не пересчитываются и не удаляются.

## Дедупликация перепечаток

При вставке нового материала:
1. Сначала проверяется точное совпадение по хэшу заголовка+текста (как на прошлом этапе).
2. Если хэш не совпал, ищется близкий по заголовку материал через `pg_trgm`
   (`similarity(title, ...) > 0.6`) в окне ±5 дней по дате публикации.

В обоих случаях новая строка не создаётся — ссылка на источник-перепечатку добавляется в
поле `reprints` (jsonb) существующей карточки упоминания.

## Переменные окружения

См. `.env.example` — все настройки (пароли, хосты БД/Redis, ключи API, интервалы опроса)
берутся из переменных окружения, ничего не захардкожено в коде.

## Тесты

```sh
cd backend
npm install
npm test
```

Покрыта главная логика этапа: сопоставление ключевых слов и их словоформ, включая фолбэк на
`manual_forms` для казахского языка (`keywords.service.spec.ts`); дедупликация по хэшу и по
похожести заголовка с записью перепечаток (`mentions.service.spec.ts`); алгоритм
автоопределения типа источника по ссылке (`source-detect.service.spec.ts`); разбор публичной
страницы Telegram-канала (`telegram.service.spec.ts`); устойчивость сборщика к падению одного
источника и фильтрация по ключевым словам (`rss.processor.spec.ts`); разбор RSS-ленты и
хеширование для дедупликации — без изменений с прошлого этапа.

## Проверка на живых данных (недели 3–4)

Прогнано на поднятом `docker compose up` стенде:

- **К-5 без RSS.** Добавлена по ссылке статья `orda.kz` (сайт без RSS вообще) — алгоритм
  корректно определил тип `parser`, тестовый сбор сразу вытащил реальные заголовок/текст/дату
  публикации из мета-тегов.
- **К-3 Telegram.** Добавлен реальный публичный канал `t.me/tengrinews` — тестовый сбор нашёл
  и сохранил 13 реальных постов без какого-либо токена.
- **≥3 разных канала с данными в базе одновременно:** RSS — 306 упоминаний (3 источника),
  Telegram — 13, парсер — 1. К-1 (NewsAPI) и К-4 (VK) корректно стоят в статусе `error` с
  понятной причиной («ключ не задан») — остальные каналы при этом продолжают работать, что и
  подтверждает изоляцию ошибок (ФТ-2).
- **Минус-слово.** Заведено минус-слово `фармацевтику`, совпадающее с текстом тестовой статьи
  `orda.kz` — при повторном сборе `itemsFilteredByKeywords: 1`, `itemsNew: 0`, в базе строка не
  появилась. После деактивации слова та же статья собралась нормально.

В процессе этой проверки на живых RSS-данных нашёлся и был исправлен реальный баг:
дедупликация по одной похожести заголовка (`pg_trgm`) склеивала как «перепечатки» разные по
содержанию ежедневные шаблонные материалы («Какая погода будет в Казахстане 18 августа» и
«…19 августа», сводки Минобороны за разные дни) — заголовки совпадают почти на 90%, хотя это
разные материалы. Исправлено: теперь помимо заголовка проверяется похожесть текста тоже (порог
ниже, т.к. текст естественно отличается сильнее), и только совпадение обоих сигналов считается
перепечаткой. Закреплено регрессионным тестом в `mentions.service.spec.ts`.
