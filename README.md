# Мониторинг упоминаний компании — MVP

Сервис ищет упоминания компании в интернете, складывает их в базу и присылает уведомления о
новых упоминаниях в Telegram-группу.

**Обновление этого этапа (ПРОМПТ 1 из 2) — самое важное изменение с прошлого этапа: `/search` и
`/status` больше не опрашивают ни один канал сбора.** Раньше `/search` последовательно дёргал RSS,
Parser, Telegram-каналы, NewsAPI, VK и объединённый веб-поиск OpenAI внутри одного HTTP-запроса —
см. историю ниже про `OnDemandSearchService` и «Бюджет времени `/search`». Новая концепция: есть
закрытый, заранее провалидированный список ссылок (`curated_links`) — каждая ссылка гарантированно
содержит упоминание компании, дату и тональность которой определяет **отдельный** скрипт (ПРОМПТ 2,
запускается вручную/по расписанию вне этого backend-процесса), а не сам бот. `/search` и `/status`
теперь **только читают уже готовые данные из БД** (`CuratedSearchService`, `backend/src/curated/`)
— никакой сети, никакого OpenAI, никакого бюджета времени на обход источников. Ограничение периода
поиска в 30 дней (было артефактом лимита Vercel Hobby 60с на весь обход каналов) снято — период
задаётся списком `SEARCH_PERIOD_DAYS` (по умолчанию от суток до 2 лет) и ограничивается только
тем, какие даты вообще есть в пуле. См. новый раздел «Закрытый пул ссылок: `/search` и `/status`»
ниже — он заменяет собой всё, что написано в старых разделах «Бюджет времени `/search`» и
«Управление ботом из группы» про поведение `/search`/`/status` **до** этого обновления (те разделы
оставлены ниже как история/архив, помечены явно). Код всех 6 каналов сбора (RSS/Parser/Telegram/
NewsAPI/VK/OpenAI web search) не тронут — они по-прежнему используются формой «Добавить по ссылке»
(`SourceOnboardingService`), просто модуль `/search` их больше не импортирует.

**Статус этапа:** боевой список источников подключён, отправка в Telegram-группу доведена до
надёжного состояния. 6 реальных сайтов (qazcloud.kz, bluescreen.kz, kz.kursiv.media, aikyn.kz,
sknews.kz, rail-news.kz) добавлены через `scripts/import-sources.ts` — тип (RSS/парсер)
определяется автоматически тем же алгоритмом, что и в форме «Добавить по ссылке» (логика теперь
живёт в общем `SourceOnboardingService`, чтобы форма и импорт не разошлись). Telegram-каналы и
соцсети пока не подключаем (соцсети — риск нарушения пользовательских соглашений при скрапинге
без официального API; каналы ещё не подобраны вручную) — `docs/sources.txt` уже поддерживает их
формат, повторный запуск импорта подхватит новые строки без правок кода. Отправка в группу:
собственная BullMQ-очередь, ограничена до ~1 сообщения/сек (Telegram rate limit), явная ошибка
в логах с указанием `chat_id`, если бота разжаловали из админов — сборщики при этом продолжают
работать. Простой фильтр «слать уведомления только по определённым `source_type`» — через
`.env`. Тональность теперь определяется автоматически через OpenAI (см. раздел «Тональность
упоминаний» ниже).

**Обновление этого этапа — редизайн фронтенда + дашборд.** Веб-интерфейс полностью пересобран на
единой дизайн-системе (см. раздел «Фронтенд: дизайн-система» ниже) и получил четвёртый раздел —
Дашборд (общее число упоминаний за период с изменением в % к предыдущему, график по дням,
распределение по тональности, топ источников). Лента теперь умеет листать за пределы первых 50
записей (пагинация) и фильтроваться (период/тональность/источник/тип источника/язык/поиск по
тексту), а тональность можно поправить прямо из карточки — см. «Ручная правка тональности» ниже.
Под это на backend добавлен один новый эндпоинт (`GET /mentions/stats`) и расширен существующий
(`GET /mentions` принимает фильтры) — подробности в разделе «API упоминаний: фильтры и `/stats`».

**Обновление этого этапа:** К-6 (поиск по всему интернету через OpenAI web search) временно
**отключён как канал сбора** флагом `SOCIAL_SEARCH_ENABLED` (по умолчанию `false`) — код канала
никуда не делся и включается обратно одной переменной в `.env`, см. раздел «К-6: временное
отключение» ниже. Тот же `OPENAI_API_KEY` теперь используется для **определения тональности**
каждого нового упоминания из любого канала (Позитив/Негатив/Нейтрал/не определена) — отдельной
BullMQ-задачей, не завязанной на К-6 и не блокирующей сбор или отправку в Telegram, см. раздел
«Тональность упоминаний» ниже.

**Обновление предыдущего этапа:** К-6 объединён в один запрос без ограничения по конкретной
площадке — раньше было 4 отдельных запроса (Instagram/Facebook/Threads/Telegram), теперь один
запрос по всему проиндексированному вебу с явным доменом-источником у каждой находки
(`mentions.source_label`). Добавлена команда бота `/search` — разовый ручной поиск за выбранный
период (кнопки: сутки…год) сразу по всем каналам.

**Обновление этого этапа (деплой на Vercel) — самое важное изменение архитектуры на сегодня.**
Backend адаптирован для деплоя на Vercel (serverless, scale-to-zero) — см. новый раздел «Деплой
на Vercel» ниже. Это потребовало убрать фоновый (по расписанию) сбор целиком:

- **BullMQ и Redis удалены из проекта.** Раньше каждый канал сбора был отдельным BullMQ
  `JobScheduler`, опрашивающим источники по таймеру; теперь таймера/очередей нет вовсе —
  упоминания собираются только по явному запросу: командой `/search` в Telegram-боте или через
  «Добавить по ссылке»/`import-sources.ts` (разовый тестовый сбор для одного источника сразу
  после добавления). Код самих каналов не тронут — убраны только обёртки-планировщики вокруг них.
- **Команды `/pause` и `/resume` убраны** — они управляли тем самым фоновым автосбором, которого
  больше нет. Оставлены `/status` и `/search`.
- **Telegram-бот переведён с long polling (`bot.launch()`) на webhook** — см. «Деплой на Vercel».
- **Индивидуальные Telegram-уведомления на каждое упоминание убраны** — раньше отдельная очередь
  `telegram-notify` слала сообщение на каждую новую находку; единственный способ получить находки
  в Telegram теперь — сводка `/search` (см. «Уведомления в Telegram» ниже).
- Определение тональности (`SentimentAnalysisService`) осталось, просто без очереди перед ним —
  считается сразу после вставки упоминания, fire-and-forget, не блокируя сам insert.

## Архитектура

- **backend/** — NestJS API, TypeORM-миграции. Никакого фонового сбора и очередей нет — все
  каналы вызываются напрямую из `/search` в Telegram-боте и из «Добавить по ссылке»
  (`SourceOnboardingService`).
- **frontend/** — React + TypeScript, единая дизайн-система (CSS Modules + токены, см. «Фронтенд:
  дизайн-система»): Дашборд, Лента упоминаний (с фильтрами и пагинацией), раздел «Источники»,
  раздел «Ключевые слова»
- **PostgreSQL** — хранилище (источники, упоминания, ключевые слова), full-text search и pg_trgm.
  Локально — контейнер `postgres` из `docker-compose.yml`; на Vercel — внешняя управляемая БД
  (Neon/Supabase), см. «Деплой на Vercel».

Внутри одного вызова `/search`/`runCollectionCycle` каждый источник обрабатывается в своём
`try/catch`: при ошибке источник помечается `status = 'error'` с человекочитаемой причиной в
`lastError`, а обработка идёт дальше по остальным источникам (ФТ-2).

## Каналы сбора

| Канал | Реализация | Почему так |
|---|---|---|
| К-1 Поисковый/новостной API | NewsAPI.org `/v2/everything` | бесплатный ключ без модерации, булев синтаксис запроса (`OR`/`NOT`/кавычки) ложится на модель ключевых слов напрямую |
| К-2 RSS | `rss-parser` + периодический глубокий проход через sitemap/К-5 (см. ниже) | лента сама по себе отдаёт только последние N материалов — глубокий проход добирает то, что уже выпало из ленты |
| К-3 Telegram | скрапинг публичной веб-версии `t.me/s/<channel>` через Cheerio | обычный Bot API требует, чтобы бот был админом канала — не подходит для произвольных публичных каналов по ссылке; MTProto требует авторизации по номеру телефона. Веб-превью отдаёт последние посты без токена и без вступления в канал |
| К-4 Соцсеть | VK API `newsfeed.search` | официальный API, приложение и `access_token` выдаются мгновенно без ручной модерации (в отличие от X/Meta), релевантно для рынка РФ/КЗ |
| К-5 Универсальный парсер | Cheerio: `og:title`/`og:description`, `<article>`, `article:published_time` и другие мета-теги даты | эвристики по ТЗ |
| К-6 Поиск по всему интернету через OpenAI web search *(временно отключён, `SOCIAL_SEARCH_ENABLED=false`)* | OpenAI Responses API, `tools: [{ type: 'web_search' }]`, один общий запрос без ограничения по домену | ключ OpenAI даёт доступ к поиску по всему проиндексированному вебу — искусственно сужать его до нескольких явно перечисленных площадок (Instagram/Facebook/Threads/Telegram) значит пропускать упоминания на форумах, в блогах, на обзорных сайтах и любых других площадках |

К-1 и К-4 не привязаны к списку ссылок админа — это глобальный поиск по активным ключевым
словам, поэтому под них при первом старте backend автоматически заводится одна системная
запись в `sources` (чтобы у них тоже был видимый статус/последний успешный сбор в UI). К-6 —
то же самое: одна системная запись `openai-search://web` («Веб-поиск (OpenAI)»).

### К-6: поиск по всему интернету через OpenAI web search

**Обновление: объединение в один запрос (было — 4 отдельных запроса по площадкам).** Раньше под
каждую площадку (Instagram, Facebook, Threads, Telegram) заводился свой запрос к Responses API с
`tools: [{ type: 'web_search', filters: { allowed_domains: [...] } }]`, где `allowed_domains`
принудительно ограничивал поиск одним доменом. Теперь это **один** запрос без `filters` вообще —
`tools: [{ type: 'web_search' }]` — покрывающий весь проиндексированный веб, а не 4 явно
перечисленных сайта. Источник/платформа каждой находки теперь определяется постфактум — из домена
фактически вернувшейся ссылки (`new URL(citation.url).hostname`), а не из заранее заданного
списка, — и сохраняется явным полем `mentions.source_label` (например, `instagram.com`,
`kz-forum.example`, `kz.kursiv.media`), которое видно и в тексте Telegram-уведомления строкой
«Источник: …», и в сводке команды `/search` (см. ниже). Старые 4 системные записи в `sources`
(по одной на площадку) при первом старте backend после этого обновления автоматически
отключаются (`status = disabled`), новая единая запись `openai-search://web` заводится вместо них
— история уже собранных упоминаний не теряется, `source_id` у них просто продолжает указывать на
теперь отключённую старую запись.

**Ограничения (важно понимать заранее).** Это поиск по уже проиндексированному открытому вебу
(инструмент `web_search` в OpenAI Responses API), а не прямой доступ к внутренним данным
соцсетей — закрытые аккаунты, приватные посты и непроиндексированные страницы так не найти.
Полностью открытая формулировка запроса (без ограничения по сайту) означает, что модель сама
решает, где искать, — это может слегка снизить долю релевантных находок на конкретной площадке
по сравнению со старым принудительным `allowed_domains`, но полностью компенсируется охватом
площадок, которые раньше вообще не рассматривались.

**Как это устроено.** Канал вызывается только из `/search` (нет больше фонового сбора вообще, см.
«Деплой на Vercel») — та же изоляция ошибок (ФТ-2), что и у остальных каналов внутри одного
вызова. Из ответа модели извлекаются только фрагменты текста,
на которые модель сама проставила `url_citation`-аннотацию (`content[].annotations`) — то есть
места, где она реально процитировала страницу с упоминанием компании, а не весь список
посещённых источников (это и есть первый фильтр от шума: страницы, которые нашлись, но не
подтвердили упоминание в тексте, не попадают в `mentions` вовсе). Дальше каждый такой фрагмент
проходит через тот же фильтр по ключевым словам (`ActiveKeywordSet`), что и все остальные
каналы, — двойная защита от ложных срабатываний.

**Важная деталь, найденная только на реальных вызовах API (не описана в документации).**
`annotation.start_index`/`end_index` иногда указывают не на цитируемое предложение, а только на
сам инлайн-маркер `([t.me](url))` — модель часто пишет одну находку на строку («N) «цитата». (ссылка)»),
и аннотация в таком случае указывает на хвостовую ссылку, а не на текст перед ней. Взятый
буквально по индексам фрагмент в этом случае получается пустым/бесполезным (проверено вживую —
первая живая попытка сохранила две записи с текстом `([t.me](https://t.me/s/...))` вместо цитаты).
Исправлено: `extractSnippet` расширяет диапазон до границ всей строки, содержащей аннотацию, и
вычищает из неё markdown-ссылки — так в базу попадает реальная цитата, а не разметка (тест на
этот конкретный случай — `openai-web-search.service.spec.ts`, «widens the snippet to the full
line…»).

Сохраняются как обычные упоминания (`mentions.source_type = 'social_search'`, `source_id`
указывает на единую запись «Веб-поиск (OpenAI)», а явный домен-источник — в
`mentions.source_label`).

**Дедупликация здесь намеренно отключена — в отличие от всех остальных каналов.** Для
сайтов/RSS/парсера дедуп (по хэшу и по похожести через `pg_trgm`) нужен, потому что одну и ту же
новость реально перепечатывают разные издания — это одна история, а не несколько. У веб-поиска
логика другая: каждый найденный результат — это отдельная, самостоятельная находка (другая
страница, другая цитата), даже если формулировка похожа на уже виденную (например, разные
страницы бизнес-справочников с одинаковым «ТОО QazCloud (Казклауд), БИН 050840009784»). Поэтому
для `source_type = 'social_search'` (`skipDedup: true` в `MentionsService.createIfNew`, задаётся в
`SocialSearchProcessor` для фонового цикла и в `OnDemandSearchService` для `/search`) ни
проверка по точному хэшу, ни проверка похожести не выполняются вовсе — каждая находка сохраняется
отдельной строкой при каждом обнаружении, в том числе повторно на следующих циклах/запросах
`/search`, если веб-поиск снова её вернёт. Чтобы не упереться в уникальность `hash` в БД (она
общая для всех каналов), у таких вставок к хэшу добавляется случайный суффикс — сам хэш при
этом больше не используется для сравнения, только для уникальности строки.

⚠ Побочный эффект, о котором стоит знать: поскольку дедуп отключён полностью, если один и тот же
результат веб-поиска попадается в нескольких фоновых циклах подряд (или в нескольких вызовах
`/search`), в Ленте и в Telegram-группе он будет появляться заново каждый раз — включая
Telegram-уведомление о «новом» упоминании (флаг `notificationSent` для таких вставок не
установлен `true` автоматически, только `isBackfill` даёт такую защиту, а тут `isBackfill: false`).
Это осознанный компромисс по вашему запросу («каждый найденный результат должен показываться
отдельно, даже если похож на уже виденный»), но если частые повторные алерты по одной и той же
статичной странице (например, собственному сайту `qazcloud.kz`) окажутся навязчивыми — дайте
знать, добавим отдельный флаг «не слать повторное уведомление, но всё равно сохранить строку».

**Модель: `gpt-5-mini`, не `gpt-4o-mini` — тоже найдено только вживую.** Документация не
уточняет, для каких моделей работает `filters.allowed_domains`; на практике `gpt-4o-mini`
(изначальный дефолт) отвечает `400 Invalid Parameter 'filters' not supported with model
'gpt-4o-mini'`. Ограничение поиска доменом площадки поддерживают только модели семейства GPT-5+
с веб-поиском — дефолт переключён на `gpt-5-mini`. Дополнительно запрос передаёт `reasoning:
{ effort: 'low' }` — понижает трату токенов на рассуждение (проверено вживую: ~250–320
reasoning-токенов вместо 1300+ при `medium`) без потери качества самого поиска.

**Стоимость и частота опроса.** Вызов инструмента веб-поиска платный — по данным OpenAI на
момент подключения (август 2026), $10 за 1000 вызовов + токены содержимого поиска по цене
модели (`gpt-5-mini`: $0.25 / 1M входных, $2.00 / 1M выходных токенов). Интервал опроса —
`OPENAI_SOCIAL_SEARCH_POLL_INTERVAL_MINUTES` (по умолчанию 45 минут); значение ниже 30 минут
игнорируется и принудительно поднимается до 30 (`SocialSearchSchedulerService`, с явным
предупреждением в логах) — платный инструмент не должен дёргаться чаще из-за опечатки в `.env`.

**Обновлено после объединения в один запрос.** Приведённая ниже оценка (7 биллинговых вызовов на
4 отдельных запроса по площадкам) относится к прежней, разделённой по площадкам реализации и
оставлена для истории. После объединения в один запрос (см. выше) на **фоновый цикл** уходит
**один** запрос к Responses API — но, как и раньше, сама модель иногда делает больше одного
внутреннего поиска (`search`/`open_page`) в рамках одного запроса, поэтому фактическое
биллинговое число (`tool_usage.web_search.num_requests`) может быть 1–2 и на объединённый запрос
тоже — ориентироваться нужно на счётчик в логах (см. ниже), а не на приведённую здесь оценку:

```
вызовов за 1 фоновый цикл (оценка) ≈ 1–2  (было 7 при 4 раздельных запросах по площадкам)
циклов в сутки  = 24 ч × 60 мин / 45 мин ≈ 32
вызовов в сутки ≈ 32 цикла × ~1–2 вызова/цикл ≈ 32–64 вызова/сутки (было ≈224)
стоимость       ≈ (32–64) × ($0.01 за вызов) + токены по цене gpt-5-mini
                ≈ $0.3–0.6/сутки (вызовы) + токены за один более длинный (без ограничения по
                  домену) запрос вместо четырёх коротких — итоговая экономия по токенам меньше
                  пропорции по числу вызовов, но общая стоимость канала ощутимо ниже, чем при
                  4 раздельных запросах
```

⚠ Точные новые цифры нужно сверить на реально поднятом стенде (см. счётчик в логах ниже) —
приведённый расчёт даёт только порядок величины, а не заменяет реальную проверку.

Исторический расчёт для прежней (раздельной по площадкам) реализации — для сравнения:

```
вызовов за 1 цикл (реально, живой прогон, старая реализация) = 7   (instagram=1, facebook=2,
                                                    threads=2, telegram=1 в первом прогоне;
                                                    1+1+2+2 во втором)
циклов в сутки  = 24 ч × 60 мин / 45 мин ≈ 32
вызовов в сутки ≈ 32 цикла × ~7 вызовов/цикл ≈ 224 вызова/сутки
стоимость       ≈ 224 × ($0.01 за вызов) + токены по цене gpt-5-mini
                ≈ $2.24/сутки (вызовы) + ~224 × (5–9 тыс. вход. + 0.5–1.6 тыс. вых. токенов)
                ≈ $2.24 + ~$0.7–1.0 (токены) ≈ $3–3.5/сутки, ~$90–100/месяц
```

**Счётчик вызовов в логах.** Каждый цикл логирует **фактическое биллинговое** число вызовов
инструмента (`payload.tool_usage.web_search.num_requests` из ответа Responses API — это то, что
реально считает OpenAI, а не число элементов `web_search_call` в `output`, которых на один
биллинговый вызов может быть несколько, например `search` + `open_page`; проверено вживую) и
накопительный счётчик с момента запуска backend (сбрасывается при перезапуске — точный биллинг
всегда смотрите в панели OpenAI usage, это только ориентир для сверки):

```
OpenAI web search (общий запрос по всему интернету): вызовов инструмента в этом запросе=1,
всего с момента запуска=7 (сверяйте с панелью OpenAI usage)
```

Разовый запрос через команду `/search` (см. ниже) логирует то же самое — плюс отдельную строку
с итоговым числом вызовов именно за этот `/search`, чтобы можно было сверить конкретный
разовый запрос с расходом в панели OpenAI, не путая его с фоновым циклом:

```
/search завершён: период=365 дн., найдено=12 (новых=3, уже известных=9), источников с
ошибкой=0, вызовов OpenAI web search за этот запрос=1 (сверяйте с панелью OpenAI usage)
```

**Настройка.** `.env`: `OPENAI_API_KEY` (обязателен для этого канала — без него источники
опрашиваются по расписанию, но остаются в статусе `error` с понятной причиной, как и К-1/К-4 без
своих ключей), `OPENAI_SOCIAL_SEARCH_MODEL` (по умолчанию `gpt-5-mini` — см. выше, почему не
`gpt-4o-mini`), `OPENAI_SOCIAL_SEARCH_POLL_INTERVAL_MINUTES` (по умолчанию 45). Ключ передаётся
только через `.env` (в `.gitignore`) — никогда не хардкодится и не логируется.

### К-6: проверка на живых данных

Прогнано на поднятом `docker compose up` стенде с реальным `OPENAI_API_KEY`:

- **Реальный ответ API.** Тестовый запрос на Telegram (`t.me`) с фильтром домена нашёл 7 реальных
  цитат из открытых Telegram-каналов, упоминающих QazCloud, с `url_citation`-аннотациями и
  ссылками вида `https://t.me/s/<channel>?...`; `tool_usage.web_search.num_requests: 1` за этот
  вызов при 5360–9034 входных и 620–1606 выходных токенах в разных прогонах (id ответа
  `resp_0245dc2049e1cbb6...`, модель `gpt-5-mini-2025-08-07`) — полный пример структуры ответа
  приведён в чате при подключении этапа.
- **Пустой результат — штатный сценарий.** Instagram и Threads по тем же ключевым словам вернули
  «упоминаний не найдено» (0 находок, `num_requests: 1`) — компания там не представлена в
  проиндексированном вебе; это не ошибка, а честный пустой результат, как и требовалось проверить.
- **Реальные упоминания дошли до Telegram-группы.** После фикса извлечения (см. выше) цикл нашёл
  9 материалов, 8 новых, все с `is_backfill=false` (источники уже прошли первый цикл) — все 8
  реально отправлены и подтверждены в логах (`Telegram notification sent for mention ...`) без
  дублей. Пример реально найденного и доставленного упоминания: канал «Фонд-бюро расследования
  коррупции» (`https://t.me/s/fund_anticorr?before=1667`) — «Нам ответил PR департамент компании
  QazCloud и попросил опубликовать опровержение.».
- **Изоляция ошибок подтверждена вживую, не только в тестах.** Первая живая попытка (с дефолтной
  моделью `gpt-4o-mini`) закончилась `sources ok=0 failed=4` — все 4 площадки упали с одинаковой
  явной ошибкой в логах (`OpenAI Responses API HTTP 400: Parameter 'filters' not supported...`),
  backend не упал, остальные 5 каналов продолжили работать по расписанию как обычно.

**Ложные срабатывания — найдены, но не в коде K-6.** Из 8 доставленных в группу материалов
только 2 реально о компании (примеры выше); остальные 6 — про выборы Курултая и реформу
образования в Кыргызстане, без единого упоминания QazCloud. Причина — в БД стенда на момент
проверки уже были активны посторонние ключевые слова `Образование` и `Курултай` (`required`,
`is_active=true`), не относящиеся к этому проекту; общий фильтр (`ActiveKeywordSet`, «совпадение
любого активного `required`-слова достаточно») сработал ровно как спроектировано — совпадение
любого активного `required`-ключевого слова считается релевантным материалом для **всех**
каналов, не только К-6. Это не дефект К-6 и не повод для минус-слов конкретно здесь — сам
поиск по «Казклауд»/«QazCloud» на живых данных ложных срабатываний не дал (обе найденные
цитаты с этими словами оказались настоящими и релевантными). **Рекомендация:** деактивировать
(или удалить) тестовые ключевые слова `Образование` и `Курултай` на вкладке «Ключевые слова»
перед боевым использованием любого канала, не только К-6.

### К-6: временное отключение

На этом этапе К-6 **временно отключён именно как канал сбора** — по флагу
`SOCIAL_SEARCH_ENABLED` в `.env` (по умолчанию `false`, т.е. отключён). Код канала
(`OpenAiWebSearchService`) не тронут и не удалён — отключение сделано так, чтобы канал можно
было включить обратно без правок кода в самом канале:

- **Системный источник `openai-search://web`** переводится в статус `disabled`
  (`SourcesService.setEnabled`) — тот же статус, что и у любого источника, выключенного вручную
  в UI. Поскольку `findActiveByType()` исключает `disabled`-источники, это же самое действие
  снимает К-6 и с разового поиска `/search`: канал просто пропускается в переборе источников, без
  отдельных проверок флага в каждом месте кода. ⚠ Нет больше фонового BullMQ-планировщика,
  который раньше зеркалил этот флаг на статус источника при каждом старте (см. «Деплой на
  Vercel») — источник нужно перевести в `active`/`disabled` вручную (через UI или БД), если флаг
  меняется после первого запуска.
- **Команда `/search`** по-прежнему работает по остальным каналам и явно сообщает в тексте
  сообщения, что веб-поиск через OpenAI временно приостановлен (см. `TelegramBotService`).
- **`OPENAI_API_KEY` при этом не простаивает** — тот же ключ используется отдельно для
  определения тональности упоминаний (см. раздел «Тональность упоминаний» ниже), независимо от
  этого флага.

**Как включить К-6 обратно:** поставьте `SOCIAL_SEARCH_ENABLED=true` в `.env`, переведите источник
`openai-search://web` в `active` (через UI или напрямую в БД — см. предупреждение выше) и
перезапустите backend.

## Тональность упоминаний (Позитив / Негатив / Нейтрал)

Каждое новое упоминание, найденное через `/search` или «Добавить по ссылке», автоматически
классифицируется по тональности через тот же `OPENAI_API_KEY`, что и К-6 — но обычным запросом
к Responses API (`SentimentAnalysisService`), **без** `tools: [{ type: 'web_search' }]` и без
связанной с ним стоимости веб-поиска: это просто классификация уже имеющегося текста
(`title` + `text`), а не поиск. Модель также возвращает короткий (1-2 предложения) нейтральный
пересказ материала (`mentions.summary`) — тем же вызовом, без отдельного запроса «сделай саммари».

**Как это работает.**

- Точка вызова — общая для всех каналов: `MentionsService.createIfNew()`, сразу после успешной
  вставки новой записи в `mentions`.
- ⚠ **Обновление (деплой на Vercel): классификация больше не идёт через очередь** — очередей в
  проекте не осталось вовсе (см. «Деплой на Vercel»). Вместо этого `createIfNew()` вызывает
  `classifySentimentInBackground()` напрямую, без ожидания (`void ...`, promise не awaitится) —
  падение или медленный ответ OpenAI не задерживает сам insert, но и не ретраится автоматически:
  ошибка один раз логируется, упоминание остаётся с `Sentiment.UNDEFINED`. Ручной пересчёт
  доступен через `npm run classify-sentiment-backfill` (см. «Как запустить»).
- ⚠ **Исключение — `/search` (on-demand-поиск).** `OnDemandSearchService` вызывает не
  `createIfNew()`, а `MentionsService.createIfNewAndClassify()`: классификация там **ожидается**
  (`await`), а не запускается в фоне, и итоговое значение `Sentiment` возвращается вызывающему —
  иначе тональность свежих находок в сводке `/search` почти всегда была бы «не определена» (сам
  fire-and-forget вызов ещё не успел бы отработать к моменту отправки сообщения в Telegram).
  Небольшая дополнительная задержка ответа здесь приемлема — у `/search` и так есть `waitUntil()`
  на несколько минут (см. «Деплой на Vercel»). Для уже известных находок (`status: 'known'`)
  тональность просто дочитывается из уже сохранённой записи, без повторной классификации. Все
  остальные каналы (сайты/RSS/Parser/Telegram/VK, `runCollectionCycle`) по-прежнему используют
  `createIfNew()` и остаются fire-and-forget без изменений.
- Модель получает системный промпт (мультиязычный — казахский/русский/английский/любой другой язык
  материала классифицируются без отдельного промпта под каждый) и обязана ответить в формате
  **structured output** Responses API (`text.format: { type: 'json_schema', strict: true }`) —
  JSON-объект `{ "sentiment": "positive"|"negative"|"neutral", "reason": "...", "summary": "..." }`,
  а не свободным текстом. Парсинг — `JSON.parse` + проверка значения по `enum Sentiment`,
  детерминированный. Результат пишется в `mentions.sentiment`/`mentions.summary`;
  `mentions.sentiment_manual` остаётся `false` — это машинная оценка, а не ручная правка человеком
  (guard `WHERE sentiment_manual = false` не даёт машинной записи затереть ручную правку, см.
  «Ручная правка тональности» ниже).
- **Если вызов упал или ответ модели не разобрать** (нет ключа, HTTP-ошибка, модель ответила не
  ожидаемым JSON) — тональность остаётся `Sentiment.UNDEFINED` («не определена», это же значение
  по умолчанию в схеме), ошибка логируется, обработка остальных упоминаний не останавливается —
  тот же принцип изоляции ошибок (ФТ-2), что и в остальных каналах.

**Пример реального вызова** (структура запроса — та же, что у К-6, но без `tools`/`reasoning`, и
с `instructions` вместо готового текста в `input`):

```json
POST https://api.openai.com/v1/responses
{
  "model": "gpt-5-mini",
  "instructions": "Ты определяешь тональность упоминания компании... (см. SentimentAnalysisService)",
  "input": "QazCloud получил награду за лучший облачный сервис\n\nКомпания отмечена жюри как...",
  "text": { "format": { "type": "json_schema", "name": "sentiment_classification", "strict": true, "schema": { "...": "..." } } }
}
```

Пример ответа и результата разбора:

```
output_text: "{\"sentiment\":\"positive\",\"reason\":\"Компания получила официальное признание отрасли.\",\"summary\":\"QazCloud получил отраслевую награду за качество облачных услуг.\"}"
→ mentions.sentiment = 'positive', mentions.sentiment_manual = false, mentions.summary = "QazCloud получил отраслевую награду за качество облачных услуг."
```

### Ручная правка тональности (ФТ-11)

- **`PATCH /mentions/:id/sentiment`**, тело `{ "sentiment": "positive" | "negative" | "neutral" |
  "undefined" }` — записывает `mentions.sentiment` и выставляет `mentions.sentiment_manual = true`.
  Недопустимое значение → `400 Bad Request`; несуществующий `id` → `404 Not Found`.
- Ручная правка (`updateSentimentManually`) всегда побеждает автоматику (`updateSentiment`) — та
  выполняет `UPDATE ... WHERE sentiment_manual = false`, поэтому уже отредактированное человеком
  упоминание молча пропускается более поздней автоклассификацией.
- **Обновление этого этапа: подключено во фронтенде.** Раньше этот эндпоинт был реализован только
  на backend — в Ленте тональность отображалась исключительно для чтения. Теперь у каждой карточки
  в Ленте есть инлайн-редактор (`SentimentSelect`, выпадающий список рядом с заголовком) — выбор
  нового значения сразу вызывает `PATCH /mentions/:id/sentiment` и обновляет карточку без
  перезагрузки страницы; ошибка сети показывается прямо под селектом, а не молча теряется.

**Где видно тональность:**

- **В сводке `/search`** — перед заголовком каждой находки эмодзи + подпись
  (🟢 Позитив / 🔴 Негатив / 🟡 Нейтрал / ⚪ Не определена), см. «`/search` — разовый поиск за
  произвольный период». Единый маппер эмодзи/подписи для бэкенда —
  `backend/src/sentiment/sentiment-display.util.ts` (используется только `TelegramBotService`,
  чтобы строки не дублировались в двух местах).
- **В карточке упоминания в UI** (`frontend/src/components/feed/MentionCard.tsx` +
  `frontend/src/components/common/SentimentBadge.tsx`/`SentimentSelect.tsx`) — цветная левая
  полоса карточки и инлайн-редактор тональности (см. «Ручная правка тональности» ниже). Единые
  hex-значения тональности для всего фронтенда — `frontend/src/styles/theme.ts` (те же значения
  задают цвет и в графиках дашборда) — см. «Фронтенд: дизайн-система».

**Настройка.** `.env`: `OPENAI_API_KEY` — тот же ключ, что и у К-6 (обязателен для этой функции;
без него тональность остаётся «не определена» для всех новых упоминаний, ошибка логируется,
остальная обработка не затрагивается), `OPENAI_SENTIMENT_MODEL` (по умолчанию `gpt-5-mini`,
можно задать отдельную более дешёвую модель независимо от модели К-6).

## API упоминаний: фильтры и `/stats`

Этот раздел описывает точечные добавления на backend, сделанные под редизайн фронтенда (Дашборд +
фильтры/пагинация в Ленте). Оба эндпоинта живут в уже существующих `MentionsController`/
`MentionsService` (`backend/src/mentions/`) — новых модулей/таблиц/миграций не потребовалось, вся
новая логика — это `WHERE`/`GROUP BY` поверх уже существующей таблицы `mentions`.

**`GET /mentions`** — раньше принимал только `limit`/`offset`. Теперь дополнительно принимает (все
необязательные, любая комбинация):

| Параметр | Значения | Что делает |
|---|---|---|
| `sentiment` | `positive` \| `negative` \| `neutral` \| `undefined` | точное совпадение по тональности |
| `sourceId` | uuid источника | точное совпадение по источнику |
| `sourceType` | `news` \| `social` \| `telegram` \| `reviews` \| `other` \| `social_search` | точное совпадение по типу источника материала |
| `language` | `ru` \| `kk` \| `en` \| ... | точное совпадение по языку (см. ограничение ниже) |
| `search` | произвольный текст | `ILIKE` по `title` и `text` (параметризованный запрос, не конкатенация SQL) |
| `period` | `today` \| `7d` \| `30d` | сахар над `dateFrom`/`dateTo` — если не задан и `dateFrom`/`dateTo` тоже не заданы, дата вообще не фильтруется (обратная совместимость: старое поведение «показать всё» сохранено) |
| `dateFrom`, `dateTo` | ISO-дата | произвольный диапазон; если заданы оба — побеждают `period` |

Дата сравнивается по `COALESCE(published_at, found_at)` — часть каналов (в первую очередь К-6) не
всегда возвращает дату публикации, и без этого фолбэка такие упоминания были бы невидимы для
любого фильтра по периоду. Форма ответа не изменилась: `{ items, total, limit, offset }`.

**`GET /mentions/stats`** (новый эндпоинт) — принимает тот же набор фильтров, что и `GET
/mentions`, но без `limit`/`offset`; если `period`/`dateFrom`/`dateTo` не заданы вовсе — по
умолчанию берётся `7d`. Возвращает:

```json
{
  "total": 48,
  "previousTotal": 0,
  "changePercent": null,
  "byDay": [{ "date": "2026-08-24", "count": 48 }],
  "bySentiment": { "positive": 9, "negative": 1, "neutral": 38, "undefined": 0 },
  "topSources": [{ "sourceId": "...", "name": "Веб-поиск (OpenAI)", "count": 47 }]
}
```

`previousTotal` считается за такой же по длительности период непосредственно перед текущим (для
`%` к предыдущему периоду на дашборде); `changePercent` — `null`, если в предыдущем периоде не было
ни одного упоминания (иначе делили бы на ноль). `topSources` — топ-10 по числу упоминаний.

**Известное ограничение: фильтр `language` пока не даёт результатов.** Колонка `mentions.language`
существует в БД (миграция `InitSchema`), но её никогда не заполняет ни один из 6 каналов сбора —
`CreateMentionInput` не содержит поля `language`, и определение языка `SentimentAnalysisService`,
хоть и знает язык материала для классификации, никуда его не пишет. Задача явно просила не трогать
сборщики/бизнес-логику сбора — поэтому сам фильтр в API есть (и селектор языка есть в UI), но пока
он всегда возвращает пустой список для любого выбранного языка, кроме случая, когда фильтр не
применён вовсе. Чтобы фильтр реально заработал, нужно отдельной задачей научить один из уже
существующих путей (например, `SentimentAnalysisService.classify`) писать определённый язык в
`mentions.language`.

Тесты на новую логику — `backend/src/mentions/mentions.service.spec.ts` (кейсы «findRecent turns
every provided filter into an andWhere clause» и «getStats computes...»), тем же стилем ручных
моков `Repository`/`DataSource`, что и остальной файл.

## Фронтенд: дизайн-система

Полный редизайн `frontend/src` — раньше три вкладки без общей дизайн-системы (инлайновые
`style={{}}` в каждом компоненте, системные шрифты, разрозненные цвета). Теперь:

- **Стилизация — CSS Modules + токены в `:root`, без Tailwind.** Проект и так был почти без
  зависимостей — CSS Modules не добавляют рантайм-зависимость (это встроенная возможность Vite),
  дают локальные имена классов без разрастания класс-атрибутов, при этом токены остаются едиными
  через глобальный `:root`. Инлайн-стили и системный подход больше не смешиваются нигде.
- **Все токены — в `frontend/src/styles/tokens.css`** (`:root`-переменные): палитра (`--color-*`,
  `--sentiment-*`), отступы (`--space-1`…`--space-6`, шкала 4·8·12·16·24·32), радиусы (только
  `--radius-sm`/`--radius-md`), единственная тень (`--shadow-popover`, только для всплывающих
  элементов), шрифты (`--font-serif`/`--font-sans`). **Любой новый компонент должен брать цвета/
  отступы/радиусы только отсюда**, а не заводить свои значения в `.module.css`.
- **Цвета тональности — одни и те же значения везде** (бейджи в Ленте, левая полоса карточки,
  инлайн-редактор, графики и легенда на Дашборде): `--sentiment-positive` `#1f7a5c`,
  `--sentiment-negative` `#a63a50`, `--sentiment-neutral` `#5b6472` (намеренно совпадает с
  `--color-ink-muted` — нейтральная тональность как «нет цветового сигнала»), `--sentiment-unknown`
  `#9aa1ac` (бейдж «не определена» — пунктирная обводка, не заливка: это отсутствие данных, а не
  четвёртый полноценный цвет). Recharts не умеет читать CSS-переменные в SVG-заливках, поэтому те
  же значения продублированы как литералы в `frontend/src/styles/theme.ts` — при смене палитры
  нужно поправить оба файла, это единственное место дублирования.
- **Типографика:** заголовки и крупные цифры — `IBM Plex Serif` (600/700), интерфейс/таблицы/текст
  — `IBM Plex Sans` (400/500/600), числовые колонки — `font-variant-numeric: tabular-nums`.
  Подключены через `<link>` на Google Fonts в `frontend/index.html` с системным фолбэком.
- **Layout:** постоянный левый сайдбар (`components/layout/AppShell.tsx`) вместо вкладок сверху —
  4 раздела (Дашборд/Лента/Источники/Ключевые слова), активный пункт отмечен левой полосой
  акцентного цвета. На узких экранах (`max-width: 860px`) сайдбар становится горизонтальным меню.
- **Переиспользуемые компоненты** — `frontend/src/components/common/`: `FilterBar` (период/
  тональность/источник/тип/язык/поиск — используется и Дашбордом в укороченном виде через проп
  `fields`, и Лентой полностью), `SentimentBadge`/`SentimentSelect`, `StatusPill`, `Pagination`,
  `LoadingState`/`ErrorState`/`EmptyState` (единое оформление трёх состояний загрузки на всех 4
  разделах, с понятным текстом и кнопкой «Повторить» у ошибки, а не голым «Загрузка…»).
- **recharts** — единственная новая зависимость (для графика по дням и легенды тональности на
  Дашборде), явно разрешена постановкой задачи; чтобы не раздувать основной бандл, `DashboardPage`
  подключается через `React.lazy` (см. `frontend/src/App.tsx`) — recharts (≈110 КБ gzip) грузится
  только при переходе в раздел «Дашборд», а не при первом открытии приложения.
- **A11y/адаптивность как база, не опция:** видимый `:focus-visible` (2px акцентный контур) на
  всех интерактивных элементах, таблицы источников/ленты — в `overflow-x: auto`-обёртке, графики —
  в `ResponsiveContainer`, все transition/animation обёрнуты в `@media (prefers-reduced-motion:
  no-preference)`.

## Как запустить

Требуется Docker Desktop (с Docker Compose).

1. Скопируйте файл с переменными окружения:

   ```sh
   cp .env.example .env
   ```

   По умолчанию там нет реальных секретов — только настройки для локального запуска.
   Для продакшена обязательно замените `DB_PASSWORD` на свой.

2. (Опционально, но нужно для К-1 и К-4) добавьте в `.env`:
   - `NEWSAPI_KEY` — бесплатный ключ на https://newsapi.org/register
   - `VK_ACCESS_TOKEN` — создайте приложение на https://vk.com/apps?act=manage, получите
     токен с правами на чтение новостной ленты

   Без этих ключей каналы К-1/К-4 будут исправно опрашиваться по расписанию, но каждый раз
   получать понятную ошибку («NEWSAPI_KEY не задан…») и оставаться в статусе `error` — это
   штатное поведение ФТ-2, не падение сервиса.

2.2. (Опционально, нужно для тональности и для К-6) добавьте `OPENAI_API_KEY` — платный ключ на
   https://platform.openai.com. Без ключа тональность новых упоминаний остаётся «не определена»
   (ошибка логируется, сбор и отправка в Telegram не затрагиваются) — см. раздел «Тональность
   упоминаний» выше. К-6 на этом этапе отключён по умолчанию (`SOCIAL_SEARCH_ENABLED=false`, см.
   раздел «К-6: временное отключение» выше) — если включите его обратно, без ключа канал так же
   остаётся в статусе `error` с понятной причиной, остальные каналы не затрагиваются.

2.1. Для Telegram-уведомлений добавьте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` — пошаговая
   инструкция (создание группы, права бота, получение chat_id) в
   [`docs/telegram-setup.md`](docs/telegram-setup.md). Без них рассылка будет падать с понятной
   ошибкой в логах на каждую попытку (сборщики данных это не останавливает).

3. Поднимите весь стек одной командой:

   ```sh
   docker compose up --build
   ```

   Это поднимет: PostgreSQL, одноразовый сервис `migrate` (накатывает миграции, добавляет
   3 реальных RSS-источника казахстанских новостных сайтов и сеет ключевые слова
   «Казклауд»/«QazCloud» с вариантами написания), backend и frontend.

4. Откройте в браузере: **http://localhost:5173**

   Слева — постоянная навигация по 4 разделам (не вкладки сверху):

   - **Дашборд** — общее число упоминаний за период с изменением в % к предыдущему, график по
     дням, распределение по тональности, топ источников; переключатель периода (сегодня/7/30 дней/
     свои даты).
   - **Лента** — упоминания с фильтрами (период/тональность/источник/тип источника/язык/поиск по
     тексту) и пагинацией; тональность можно поправить прямо в карточке.
   - **Источники** — таблица источников (тип/статус/дата последнего успешного сбора/число
     упоминаний) и форма «добавить по ссылке».
   - **Ключевые слова** — обязательные/точные фразы и минус-слова в двух отдельных таблицах.

   ⚠ Если `.env` содержит `VITE_API_URL` с адресом внешнего (например, задеплоенного на Vercel)
   backend, фронтенд при локальной сборке обратится именно туда, а не к локальному backend на
   порту 3000 — для полностью локального стенда либо уберите/закомментируйте эту переменную в
   `.env`, либо явно переопределите её перед сборкой: `VITE_API_URL=http://localhost:3000 docker
   compose up --build`.

5. Логи сборщиков видно в выводе backend-контейнера:

   ```sh
   docker compose logs -f backend
   ```

   Ищите строки `<Канал> cycle start` / `<Канал> cycle done` — видно, сколько источников
   опрошено, сколько материалов найдено/новых/перепечаток/отфильтровано по ключевым словам.

## Как бот получает апдейты: polling локально, webhook на Vercel

У бота два транспорта, и ни один из них не работает в обеих средах — поэтому режим выбирается
автоматически (`resolveTelegramBotMode()`, `backend/src/notifications/telegram/telegram-bot-mode.util.ts`):

| Среда | Режим по умолчанию | Почему |
|---|---|---|
| `docker compose up` (локальный стенд) | `polling` | Telegram не может сделать HTTP-запрос на `http://localhost:3000` — вебхук туда никогда не доедет, и бот молча не отвечает ни на что |
| Vercel | `webhook` | инстанс функции замораживается между запросами, постоянное соединение `getUpdates` на нём не живёт |

Определяется это по переменной `VERCEL`, которую Vercel проставляет сам — на деплое ничего
дополнительно прописывать не нужно. Переопределить можно явно: `TELEGRAM_BOT_MODE=polling` или
`TELEGRAM_BOT_MODE=webhook` в `.env` (например, `webhook`, если локальный стенд выставлен наружу
через ngrok/туннель, — тогда не забудьте `npm run set-webhook -- https://<ваш-туннель>`).

В режиме `polling` бот стартует в `TelegramBotService.onModuleInit()` и останавливается в
`onModuleDestroy()` (работает благодаря `app.enableShutdownHooks()` в `main.ts`). Два нюанса,
которые там намеренно сделаны именно так:

- `launch()` у Telegraf резолвится только когда бот **останавливается**, поэтому его нельзя
  `await`'ить в `onModuleInit()` — Nest никогда бы не закончил bootstrap и HTTP-сервер не начал бы
  слушать порт. Ждём колбэк `onLaunch` (срабатывает сразу после успешного `getMe()`), так что
  неверный токен виден в логах как явная ошибка, а не как тишина.
- Если polling не стартовал (неверный/отозванный токен, нет сети) — ошибка пишется в лог, но
  backend поднимается дальше: REST API, фронтенд и скрипты пула не должны падать из-за бота.
- `dropPendingUpdates: true` — всё, что накопилось, пока стенд лежал, протухло по определению:
  ответ `/search` за период, который давно прошёл, хуже, чем отсутствие ответа.

### Бот не отвечает в группе — что проверить

1. `docker compose logs backend | grep TelegramBot` — в логе должна быть строка **«Telegram-бот
   запущен в режиме long polling»**. Если вместо неё `TELEGRAM_BOT_TOKEN не задан` — токен пустой
   в `.env` (см. `docs/telegram-setup.md`), бот вообще не создаётся.
2. `TELEGRAM_CHAT_ID не задан` в логе — бот запустится, но отклонит **любую** команду как «не из
   рабочей группы» (`isAuthorizedChat()`); получите id через `npm run get-chat-id`.
3. `Отклонена команда из неавторизованного чата (chat_id=…)` — команда пришла не из той группы,
   что прописана в `TELEGRAM_CHAT_ID`; сверьте значения (у супергрупп id со знаком «минус»).
4. `401: Unauthorized` — токен неверный или отозван через `/revoke` у @BotFather.
5. Обе `.env` — в корне репозитория (её читает `docker compose`) и `backend/.env` (её читает
   `npm run start:dev` и скрипты из `src/scripts`). Заполнять нужно ту, из которой вы запускаете.

## Деплой на Vercel

Backend адаптирован для деплоя на Vercel как serverless-функция на базе Docker-образа
(`backend/Dockerfile.vercel`). Это принципиально другая среда исполнения, чем `docker compose up`
локально, и из этого вытекают все отличия ниже:

- **Stateless, scale-to-zero.** Функция «замораживается»/уничтожается после ~5 минут простоя (на
  preview-деплоях — уже через ~30 сек), и следующий запрос стартует новый инстанс с нуля. Отсюда —
  фоновый сбор по расписанию убран полностью (см. «Архитектура» выше): держать открытым постоянный
  воркер, ожидающий следующего тика таймера, на такой платформе не получится. Вместо этого сбор
  происходит только по явному запросу — командой `/search` в Telegram или через «Добавить по ссылке».
- **Long polling не работает.** По той же причине — `bot.launch()` держит открытым постоянное
  соединение `getUpdates` к Telegram, а инстанс, который его держит, будет заморожен. **На Vercel**
  бот работает через webhook: Telegram сам делает HTTP-запрос на backend на каждое новое
  сообщение/нажатие кнопки (`POST /telegram/webhook`, `TelegramWebhookController` →
  `TelegramBotService.handleUpdate()`). ⚠ Обратное тоже верно и стоило нам работающего бота на
  локальном стенде: webhook не работает на `docker compose up` — Telegram физически не может
  постучаться в `http://localhost:3000`. Поэтому транспорт теперь выбирается по среде, см.
  «Как бот получает апдейты» ниже.
- **Нужна внешняя Postgres.** Локальный контейнер `postgres` из `docker-compose.yml` недоступен
  извне — для Vercel нужна managed Postgres (например, [Neon](https://neon.tech) или
  [Supabase](https://supabase.com), у обоих есть бесплатный тир со строкой подключения с SSL).

### Переменные окружения для Vercel

| Переменная | Обязательна | Назначение |
|---|---|---|
| `PORT` | нет (задаёт Vercel сам) | порт, который слушает `main.ts` |
| `DATABASE_URL` | да | строка подключения к внешней Postgres (Neon/Supabase), `sslmode=require`; имеет приоритет над `DB_HOST`/`DB_PORT`/... |
| `TELEGRAM_BOT_TOKEN` | да, если нужен бот | токен от @BotFather |
| `TELEGRAM_CHAT_ID` | да, если нужен бот | id рабочей группы, см. `docs/telegram-setup.md` |
| `TELEGRAM_WEBHOOK_SECRET` | да, если нужен бот | случайная строка, сверяется с заголовком `X-Telegram-Bot-Api-Secret-Token` на каждом вебхуке |
| `OPENAI_API_KEY` | нет (без него — тональность «не определена») | тональность + К-6, если включите обратно |
| `NEWSAPI_KEY` | нет | только если включаете К-1 обратно |
| `VK_ACCESS_TOKEN` | нет | то же самое для К-4 |

`DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME`/`DB_SSL` **не нужны на Vercel** — это
fallback только для локального `docker-compose`, `DATABASE_URL` их полностью перекрывает.

### Пошаговая инструкция

⚠ **Примечание про имя файла.** Файл называется `backend/Dockerfile` (не `Dockerfile.vercel`,
несмотря на то, что более ранние версии этого README называли его так) — обнаружено при проверке
этого этапа. Команды ниже используют актуальное имя.

1. **Сборка образа локально (проверка перед первым деплоем).**

   ```sh
   cd backend
   docker build -f Dockerfile -t qazcloud-backend-vercel .
   ```

2. **Первый деплой.** В настройках проекта на Vercel укажите `backend/Dockerfile` как Dockerfile
   для сборки (Vercel → Project Settings → Build & Development Settings), впишите переменные
   окружения из таблицы выше (Project Settings → Environment Variables), затем:

   ```sh
   vercel --prod
   ```

   (или через обычный git-деплой, если репозиторий подключён к Vercel напрямую). `vercel.json` в
   корне репозитория задаёт `maxDuration: 60` для функции — но и это уже верхняя граница: на
   бесплатном (Hobby) тарифе Vercel **любой** вызов функции жёстко обрывается через 60 секунд
   независимо от того, что написано в `vercel.json` (это не настраиваемый лимит, а свойство тарифа
   — поднять его может только платный план). ⚠ Это раньше ограничивало период `/search` 30 днями и
   требовало собственного бюджета времени внутри самого `/search` (см. историческую секцию
   «Бюджет времени `/search`» ниже) — теперь `/search` только читает БД (см. «Закрытый пул ссылок:
   `/search` и `/status`» выше), поэтому 60-секундный потолок Vercel для него практических
   последствий больше не имеет (обычный SQL-запрос укладывается в это время на порядки быстрее).

3. **Разовый прогон миграций против облачной БД.** Миграции **намеренно не запускаются
   автоматически** ни при сборке образа, ни при каждом холодном старте функции (см. комментарий в
   `Dockerfile`) — гонять их параллельно на нескольких serverless-инстансах ненадёжно. Прогоняйте
   вручную после каждого релиза, меняющего схему (актуально и для миграции `CuratedLinks` из этого
   этапа — накатите её на облачную БД так же, этой командой):

   ```sh
   cd backend
   DATABASE_URL="postgres://user:pass@host/db?sslmode=require" npm run migration:run
   ```

4. **Разовая регистрация вебхука.** После того как первый деплой получил постоянный URL:

   ```sh
   cd backend
   TELEGRAM_BOT_TOKEN=... TELEGRAM_WEBHOOK_SECRET=... npm run set-webhook -- https://your-app.vercel.app
   ```

   Повторять нужно только если поменялся URL деплоя (например, подключили свой домен) — не на
   каждый деплой.

### Почему обработчики бота дожидаются всего синхронно, а не через `waitUntil()`

⚠ **Актуальное решение (текущий деплой), актуально и после перехода `/search`/`/status` на закрытый
пул ссылок (см. верх README).** Каждый обработчик команды/кнопки в `TelegramBotService` **дожидается**
всей своей работы (`CuratedSearchService.search()`/`findPage()`/`getPoolStats()` — это просто
запросы к БД, но всё равно `await`) целиком, прямо в рамках того же вызова вебхука, и только потом
отвечает в чат — то есть без всякого `waitUntil()`/fire-and-forget. `TelegramWebhookController`
дожидается `TelegramBotService.handleUpdate()`, которая дожидается самого обработчика Telegraf.

Раньше (пока `/search` ещё опрашивал живые каналы через `OnDemandSearchService.runSearch()`) здесь
стоял `waitUntil()` из `@vercel/functions`: обработчик отвечал на вебхук сразу и не дожидался
`runSearch()`, полагаясь на то, что платформа не заморозит инстанс, пока обёрнутый promise не
завершится. **На практике это не сработало**: этот деплой поднимается на Vercel как
"Container"-функция — она стартует свежий процесс на каждый вызов (в логе виден полный bootstrap
Nest на каждый запрос) и убивает его сразу после ответа на вебхук, независимо от `waitUntil()`.
Соединение с БД (TypeORM) обрывалось прямо посреди работы («Driver not Connected»), и ответ в
Telegram просто не приходил. Awaiting здесь — не временная мера, а то, что реально работает на этом
деплое; **не предлагайте вернуться к `waitUntil()`/fire-and-forget** как решение проблемы с
бюджетом времени — эта дорога уже проверена и не работает именно на этом деплое.

⚠ **Историческая секция — только для институциональной памяти, к текущему `/search` не относится.**
Раздел «Бюджет времени `/search`» ниже (`SEARCH_TIME_BUDGET_MS` и другие переменные) описывал
собственный тайм-бюджет `OnDemandSearchService.runSearch()`, когда `/search` последовательно
опрашивал RSS/Parser/Telegram/NewsAPI/VK/OpenAI web search внутри лимита Vercel Hobby в 60с.
`OnDemandSearchService` **удалён** вместе с модулем `search-on-demand` — `/search` теперь только
читает БД (`CuratedSearchService`), поэтому весь этот тайм-бюджет и связанные переменные окружения
(`SEARCH_TIME_BUDGET_MS`, `SEARCH_DEEP_SCAN_PHASE_BUDGET_MS`, `PARSER_ONDEMAND_*`) удалены из
`.env.example`. Текущая семантика периода `/search` описана в разделе «Закрытый пул ссылок:
`/search` и `/status`» ниже.

### Бюджет времени `/search` (историческая секция, см. предупреждение выше)

`OnDemandSearchService.runSearch()` опрашивает все каналы (RSS, Parser, Telegram, NewsAPI, VK,
OpenAI web search) и все их источники строго последовательно, `await`, в рамках одного HTTP-
вызова — а он жёстко ограничен потолком Vercel Hobby в 60 секунд (см. выше). Добавление полноценного
глубокого обхода для PARSER-источников (см. «Исправление: PARSER-источники не проходили глубокий
обход» ниже) сделало этот риск конкретным: у одного PARSER-источника без sitemap обход даже одной
страницы листинга — это десятки HTTP-запросов подряд (по одному на статью), и уже это одно легко
съедает 40+ секунд (см. результаты прогона на sknews.kz там же).

**Меры (`on-demand-search.service.ts`):**

- **Общий дедлайн на весь `/search`-вызов** — `SEARCH_TIME_BUDGET_MS` (по умолчанию 45000, с
  запасом от 60с под сериализацию ответа, отправку сообщений в Telegram и накладные расходы
  Nest/БД). Перед обработкой **каждого** источника в цикле (по всем каналам, не только Parser)
  проверяется `Date.now() < deadline`; при исчерпании бюджета источник помечается пропущенным
  (`sourcesFailed` с текстом «пропущено: не хватило времени в рамках лимита Vercel (60с)...»), а
  цикл продолжает быстро домаркировывать оставшиеся источники тем же способом — ни один реальный
  сетевой запрос после исчерпания бюджета уже не выполняется. Итоговое сообщение в Telegram
  отправляется в любом случае — молчания при исчерпании бюджета не бывает (см.
  `TelegramBotService.runOnDemandSearchAndReport`, которое дожидается `runSearch()` целиком и
  ловит даже полный сбой).
- **Отдельный, более тесный дедлайн на один источник — и для RSS-канала, и для Parser-канала**
  (оба в итоге вызывают один и тот же `ParserService.deepCollect()`) — `PARSER_ONDEMAND_SOURCE_
  BUDGET_MS` (по умолчанию 10000) — `min(общий_дедлайн, now + PARSER_ONDEMAND_SOURCE_BUDGET_MS)`,
  прокидывается в `deepCollect()` и дальше в `crawlSite()`/`collectUrlsFromSitemaps()`, где
  проверяется перед каждой отдельной сетевой операцией (загрузка следующей страницы листинга,
  следующего файла sitemap, разбор очередной статьи) — цикл останавливается на середине и отдаёт
  то, что уже успел собрать, а не падает и не продолжает до конца списка. Так один медленный/
  большой сайт не съедает весь `SEARCH_TIME_BUDGET_MS` и не лишает шанса остальные источники.
  ⚠ **Реальный инцидент, из-за которого этот пункт распространили и на RSS-канал (не только на
  Parser).** Сразу после первого деплоя этого фикса `/search` вернул «не удалось опросить» почти
  по всему списку источников сразу — RSS, Parser, Telegram, VK, даже канал К-6 (0 вызовов OpenAI
  web search). Причина: общий дедлайн (`SEARCH_TIME_BUDGET_MS`) был добавлен и корректно
  проверялся перед каждым источником, но сам глубокий проход RSS-канала (`fetchRssWithDeepScan` →
  `deepCollect()`) изначально не получал `deadline` вообще — он остался полностью неограниченным
  по времени. RSS — первый канал в списке `channels`, поэтому хватило одного-двух RSS-источников,
  у которых как раз подошло время планового глубокого прохода (`last_deep_scan_at` протух), чтобы
  съесть все 45 секунд бюджета целиком ещё до того, как очередь дошла до остальных каналов — и всё,
  что шло после, корректно, но массово помечалось как «пропущено по тайм-ауту». Ответ пользователю
  пришёл (молчания не было — это сработало, как и задумано), но полезность была нулевой. Исправлено:
  `fetchRssWithDeepScan` тоже принимает `budget` (опционально — по умолчанию не ограничен, чтобы не
  ломать вызовы без бюджета) и в `on-demand-search.service.ts` получает ровно тот же
  `PARSER_ONDEMAND_*`-бюджет, что и Parser-канал, а не отдельный собственный.
- **Отдельный (меньший) бюджет специально на фазу глубокого обхода (RSS + Parser вместе)** —
  `SEARCH_DEEP_SCAN_PHASE_BUDGET_MS` (по умолчанию 30000, из общих 45000) — источники этих двух
  каналов проверяются против `min(общий_дедлайн, старт + SEARCH_DEEP_SCAN_PHASE_BUDGET_MS)`, а не
  напрямую против общего дедлайна; все остальные каналы (Telegram, NewsAPI, VK, OpenAI web search)
  по-прежнему проверяются против полного `SEARCH_TIME_BUDGET_MS`. ⚠ **Второй реальный инцидент,
  из-за которого появился этот пункт.** После миграции у *каждого* существующего источника
  `last_deep_scan_at` был `NULL` — значит на самом первом `/search` после деплоя фикса *все* RSS- и
  Parser-источники сразу оказались «due» для полного одноразового прохода на `BACKFILL_DAYS`
  одновременно, в одном и том же вызове. Общего 45-секундного бюджета хватило в лучшем случае на
  3–5 источников (при лимите ~10с на источник) — и все каналы, идущие в очереди *после* RSS/Parser
  (Telegram, NewsAPI, VK, К-6), ни разу не получили своего хода: бюджет заканчивался ещё на фазе
  RSS+Parser. Итог — почти весь список источников (включая лёгкие, не связанные с deep scan вообще,
  например VK) снова показывал «не удалось опросить», хотя реальной поломки не было — просто
  очередь на разовый глубокий проход "холодного старта" оказалась намного длиннее одного 45-секундного
  окна. Резервирование отдельного, меньшего под-бюджета на RSS+Parser не устраняет сам бэклог
  (он рассасывается постепенно — за несколько `/search`-вызовов, по мере того как уже обработанные
  источники перестают быть «due» на `RSS_DEEP_SCAN_INTERVAL_HOURS`), но гарантирует, что лёгкие,
  однократные каналы больше никогда не остаются совсем без хода из-за этого бэклога.
- **Уменьшенные лимиты специально для рутинного прохода `/search`** —
  `PARSER_ONDEMAND_MAX_ARTICLES` (15, вместо `PARSER_MAX_SITEMAP_ARTICLE_URLS`/
  `PARSER_MAX_ARTICLES_PER_CRAWL` = 60 по умолчанию) и `PARSER_ONDEMAND_CRAWL_DELAY_MS` (150мс,
  вместо `PARSER_CRAWL_DELAY_MS` = 400мс) — те дефолты рассчитаны на разовый онбординг одного
  источника («Добавить по ссылке» — там свой, куда более щедрый бюджет,
  `PARSER_ONBOARDING_SOURCE_BUDGET_MS` = 45000, потому что это всегда ровно один источник на весь
  HTTP-запрос), а не на «сколько угодно источников, созревших для глубокого прохода в одном общем
  `/search`-вызове».
- **Троттлинг `last_deep_scan_at` остаётся обязательным** и для PARSER-источников без исключений
  (см. ниже) — большинство вызовов `/search` тратят время только на дешёвую проверку "не пора ли"
  и не запускают дорогой sitemap/crawl вообще. Но троттлинг сам по себе не гарантирует, что в
  одном конкретном `/search`-вызове не "созреет" сразу несколько источников — общий дедлайн выше
  всё равно нужен как страховка на этот случай.
- **`SEARCH_PERIOD_OPTIONS` не трогали** — максимум остался 30 дней («Месяц»), увеличивать его
  обратно не пытались (см. предупреждение в `telegram-bot.service.ts` про инцидент с «Годом»).

**Прогон нагрузочного сценария (см. «Проверка на живых данных» ниже, раздел про PARSER-фикс)** —
поскольку в этой среде недоступен Docker для полноценного `docker compose up` со всей БД (см. тот
же раздел), нагрузочная проверка сделана на уровне `ParserService.deepCollect()` напрямую против
живого sknews.kz — самого медленного из известных в проекте PARSER-источников без рабочего sitemap
— с ровно теми же параметрами, что и в реальном `/search`-вызове
(`PARSER_ONDEMAND_MAX_ARTICLES=15`, `PARSER_ONDEMAND_CRAWL_DELAY_MS=150`,
`PARSER_ONDEMAND_SOURCE_BUDGET_MS=10000`): обход корректно остановился ровно на границе бюджета
(**10160мс**), собрав 6 из 15 запрошенных статей вместо зависания на полной пагинации. Полная
проверка «несколько таких источников одновременно, вызов `/search` целиком, лог `/search
завершён за …мс`» осталась на совести деплоя со стендом — механизм дедлайна (общий + на источник)
покрыт и модульными тестами (`on-demand-search.service.spec.ts`,
`parser-deep-scan.util.spec.ts`, `parser.service.spec.ts`), которые проверяют его детерминированно
без реальной сети.

## Источники (US-2)

Список хранится в БД (таблица `sources`), редактируется через UI на вкладке «Источники»:

- **Добавление по ссылке.** Алгоритм автоопределения типа:
  1. ссылка на `t.me/...` или `@channel` → канал К-3 (Telegram);
  2. иначе проверяем, есть ли RSS/Atom-лента — сама ссылка уже валидный фид, либо в её HTML
     есть `<link rel="alternate">`, либо фид лежит по стандартному пути (`/rss`, `/feed`,
     `/rss.xml`, `/feed.xml`, `/atom.xml`) → канал К-2 (RSS);
  3. иначе → канал К-5 (универсальный парсер страницы).

  Сразу после добавления источник опрашивается один раз («тестовый сбор») — админ сразу
  видит либо «нашлось N материалов», либо понятную причину ошибки текстом (не стектрейс).

- **Отключение/удаление.** Источник можно отключить (перестаёт опрашиваться, но остаётся в
  списке) или удалить — ранее собранные упоминания при этом остаются в базе
  (`mentions.source_id` становится `NULL`).

### Массовый импорт списка источников

`backend/src/scripts/import-sources.ts` — читает `docs/sources.txt` (по одному URL на строку,
`#`-строки и пустые строки игнорируются) и добавляет каждый через тот же
`SourceOnboardingService`, что и форма «добавить по ссылке» в UI — код не задублирован. Для
каждого сразу же выполняется тестовый сбор.

```sh
docker compose run --rm migrate npm run import-sources
```

(нужен именно `migrate`/`backend`-контейнер — там доступен Postgres по имени `postgres`, как у
самого backend; голый запуск на хосте это имя не разрешит). Скрипт идемпотентен
— уже добавленные URL просто помечаются `SKIP` при повторном запуске, так что им же добавляются
и новые строки (например Telegram-каналы вида `t.me/<channel>` или соцсети — формат ссылки в
файле уже поддержан, автоопределение типа само разберёт их канал при следующем запуске, без
правок кода). Пример реального прогона (6 сайтов из стартового списка):

```
OK    https://qazcloud.kz/       -> тип=parser, найдено=1,    новых=1,   отфильтровано=0
OK    https://bluescreen.kz/     -> тип=rss,    найдено=15,   новых=0,   отфильтровано=15
OK    https://kz.kursiv.media/   -> тип=rss,    найдено=100,  новых=0,   отфильтровано=100
OK    https://aikyn.kz/          -> тип=rss,    найдено=1000, новых=0,   отфильтровано=1000
OK    https://sknews.kz/         -> тип=parser, найдено=1,    новых=0,   отфильтровано=1
OK    https://rail-news.kz/      -> тип=parser, найдено=1,    новых=0,   отфильтровано=1
```

Все 6 подключились с первой попытки (0 failed). Единственное реальное совпадение с ключевым
словом — собственная главная страница `qazcloud.kz` («QazCloud | Облачные решения») — попало в
базу как `is_backfill=true` (первый цикл источника), поэтому в группу не ушло; это ожидаемое
поведение backfill-режима, а не баг. Остальные 1117 материалов из 5 других сайтов ключевым
словам не совпали вообще — ложных срабатываний «Казклауд»/«QazCloud» на реальных данных не
найдено, минус-слова пока не нужны.

### Исключение доменов (blacklist)

`EXCLUDED_DOMAINS` в `.env` — comma-separated список доменов, которые никогда не должны попасть
ни в `sources`, ни в `mentions`. Каждый домен в списке автоматически покрывает и свои поддомены
(`qazcloud.kz` в списке блокирует и `cloud.qazcloud.kz`). Список читается `DomainExclusionService`
(`backend/src/common/domain-exclusion.service.ts`) напрямую из `process.env` — расширить список
можно правкой `.env` без пересборки кода.

Применяется в двух точках:

1. **`SourceOnboardingService.addByLink`** — если админ (через форму или `import-sources.ts`)
   пытается добавить источник с доменом из списка, ссылка отклоняется ещё до попытки её
   раскрыть/опросить: `BadRequestException` с понятной причиной «домен в списке исключений»,
   запись в `sources` не создаётся.
2. **`runCollectionCycle`** (`backend/src/common/collector-run.util.ts`) — общая точка вставки
   упоминаний для всех каналов проверяет домен `item.url` тем же сервисом перед вставкой в
   `mentions`, тем же шагом, что и фильтр по ключевым словам. Это единственный способ отсечь
   находку из **К-1** (NewsAPI) или **К-6** (веб-поиск OpenAI) — у этих каналов нет фиксированного
   списка сайтов, они ищут по всему интернету и теоретически могут вернуть заблокированный домен
   сами. Отфильтрованные так находки считаются отдельно (`itemsFilteredByExcludedDomain` в логах
   цикла сбора), в базу не попадают.

Источники, уже добавленные в `sources` до появления домена в блэклисте, не остаются висеть
активными: при каждом старте backend `DomainExclusionEnforcerService`
(`backend/src/sources/domain-exclusion-enforcer.service.ts`) проходит по всей таблице `sources` и
переводит в `disabled` любую запись, чей домен подпадает под `EXCLUDED_DOMAINS` — тем же способом,
как если бы админ вручную отключил источник. Так, при первом же деплое этой фичи, свой собственный
`https://qazcloud.kz/` (добавленный ранее как обычный источник К-5) был автоматически переведён в
`disabled` — уже собранные по нему упоминания остались в базе нетронутыми.

Стартовый список (можно расширять только правкой `.env`, без изменений кода):

```
EXCLUDED_DOMAINS=goszakup.gov.kz,zakup.nationalbank.kz,qazcloud.kz,cloud.qazcloud.kz
```

## Ключевые слова (US-3)

Вкладка «Ключевые слова»: обязательные слова, минус-слова, точная фраза в кавычках.

- Правило фильтрации: если активных обязательных/точных ключевых слов нет вообще — фильтр
  выключен, идёт всё подряд (как на прошлом этапе). Если есть — материал должен совпасть
  хотя бы с одним обязательным/точным ключевым словом и не совпасть ни с одним минус-словом.
- **Морфология.** Для русского (`language = ru`, без ручных словоформ) совпадение ищется
  через `to_tsvector('russian', ...) @@ plainto_tsquery('russian', ...)` — учитывает падежи/
  склонения автоматически. Для казахского в Postgres нет готового FTS-словаря, поэтому по
  умолчанию (`language = kk`) используется явный список словоформ (`manual_forms`), заданный
  вручную через запятую в форме добавления — совпадение ищется как обычная подстрока по
  каждой форме. Это же ручное поле можно включить и для русских ключевых слов, если
  автоматическая морфология не устраивает.
- Изменение списка применяется только к следующему циклу сбора: каждый цикл сборщика один
  раз загружает снимок активных ключевых слов и использует его до конца цикла — уже
  собранные упоминания не пересчитываются и не удаляются.
- Засеяны реальные ключевые слова для этого этапа: `Казклауд` (+ форма «Каз Клауд») и
  `QazCloud` (+ форма «Qaz Cloud») — регистр букв значения не имеет, совпадение ищется как
  подстрока (`manual_forms`), а не через FTS, потому что это название бренда, а не обычное
  словарное слово.
- ⚠ **Обновление: два минус-слова, `Астана` и `медицина`** (`npm run seed:minus-keywords`,
  `backend/src/seed/seed-minus-keywords.ts`) — добавлены после того, как реальный сбор накопил
  заметный объём ложных срабатываний: новости про столицу (дороги, погода, выборы, спорт) и
  медицинские материалы, никак не связанные с QazCloud, см. «Очистка нерелевантных упоминаний»
  ниже. Обе записи заданы через `manual_forms` с усечённой русской основой (`Астан`, `медицин`), а
  не через обычный FTS-путь для `language = 'ru'` — на реальных данных проекта
  Postgres-полнотекстовый поиск ненадёжно склоняет оба слова (`to_tsvector('russian', 'в
  Астане...')` не совпадает с `plainto_tsquery('russian', 'Астана')`, аналогично для
  «медицинская»/«медицина»), а усечённая основа ловит все словоформы одной подстрокой — тот же
  приём, что и у `cleanup-unrelated-mentions.ts`. **Плюс английская форма у каждого**
  (`Astana`, `medic`) — ни одна из русских основ не совпадает с латиницей, а в реальных данных
  встречаются англоязычные ложные срабатывания (`astana_hub`, статья про «AI-Sana in Kazakhstani
  universities», где в тексте упоминается medicine/medical). `Astana` не склоняется в английском,
  поэтому взята целиком; `medic` — та же усечённая основа, что и у русской, чтобы ловить
  medical/medication/biomedical одной подстрокой. Казахский отдельной формой не заведён —
  падежные окончания в казахском лишь дописываются после основы (Астана → Астанада/Астанаға/...),
  поэтому усечённая кириллическая основа `Астан` уже покрывает его без дополнительной записи.
  ⚠ **Важно:** в таблице `keywords` на момент внедрения уже был активный **REQUIRED**-ключ
  `Астана` — судя по всему, и есть настоящая причина накопившихся ложных срабатываний (любой
  материал с упоминанием столицы проходил фильтр как «релевантный»). Минус-слово всегда
  побеждает обязательное при совпадении (см. `ActiveKeywordSet.match`), так что новые ложные
  находки уже не создаются — но старый REQUIRED-ключ `Астана` стоит вручную проверить и,
  если он не нужен, деактивировать/удалить через вкладку «Ключевые слова» в UI
  (`seed-minus-keywords.ts` печатает явное предупреждение об этой коллизии при каждом запуске,
  пока она не устранена).
  ⚠ **Известный компромисс:** минус-слово `Астана` также подавит вставку будущего *настоящего*
  упоминания о QazCloud, если оно одновременно называет город компании (например, ещё одна
  выписка из госреестра вида «ТОО QazCloud... г. Астана») — минус-слова в этом проекте не умеют
  «побеждать только когда бренд не упомянут», это ограничение самого механизма
  `ActiveKeywordSet`, не что-то specific для этой пары слов.

## Очистка нерелевантных упоминаний

Разовый maintenance-скрипт `backend/src/scripts/cleanup-unrelated-mentions.ts` — убирает из уже
накопленной базы записи, которые туда попали до того, как появились минус-слова выше (или в
принципе не связаны с QazCloud). Не эндпоинт — ручная операция, запускается из терминала, по
образцу `import-sources.ts`/`classify-sentiment-backfill.ts`.

**Что удаляется** (объединение, дубликаты не считаются дважды):

- **(а) не связаны с QazCloud вообще** — `ActiveKeywordSet.match(title, text)` (тот же матчер,
  что и у реального сбора/`/search`, через `KeywordsService`) возвращает `matched: false`.
- **(б) ложные срабатывания «Астана»/«медицина»** — заголовок или текст содержат усечённую
  основу `астан`/`медицин`/`astana`/`medic` без учёта регистра (не полное слово — см.
  предупреждение в разделе «Ключевые слова» выше про пропущенные русские словоформы и
  латиницу).
- **Защита от переудаления.** Запись, независимо подтверждённая как реально относящаяся к
  QazCloud через настоящий бренд-ключ (`Казклауд`/`QazCloud`/... — не через сам буквенный
  REQUIRED-ключ `Астана`, который сюда намеренно не считается «брендовым»), никогда не удаляется
  ни по причине (а), ни по причине (б) — даже если содержит «Астана»/«медицина». Пример из
  реальных данных: карточка из госреестра «ТОО QAZCLOUD (КАЗКЛАУД), Г.АСТАНА» осталась цела.
- Записи с `sentiment_manual = true` **не защищены** от удаления — это поле относится только к
  ручной правке тональности (ФТ-11), а не к релевантности упоминания компании, так что относиться
  к ней как к «не трогать» не было оснований в требованиях этой задачи.

**Запуск (dry-run по умолчанию — ничего не удаляет, только печатает счётчики и примеры):**

```sh
cd backend
npm run cleanup-mentions
```

**Реальное удаление** — только с явным флагом:

```sh
npm run cleanup-mentions -- --execute
```

**На удалённой БД (Vercel/Neon/Supabase)** — так же, как `migration:run` (см. «Деплой на Vercel»):

```sh
cd backend
DATABASE_URL="postgres://user:pass@host/db?sslmode=require" npm run cleanup-mentions
DATABASE_URL="postgres://user:pass@host/db?sslmode=require" npm run cleanup-mentions -- --execute
```

Локально с `docker-compose` (использует хостнейм `postgres`, как у `migrate`/`backend`):

```sh
docker compose run --rm migrate npm run cleanup-mentions -- --execute
```

**Проверено на реальных данных этого этапа** (149 упоминаний в базе на момент проверки):
причина (а) — 0 записей до добавления минус-слов (потому что REQUIRED-ключ `Астана` делал почти
всё «релевантным»), 101 после (как только «Астана»/«медицина» стали минус-словами, тот же
`ActiveKeywordSet.match` естественно перекрыл обе причины); причина (б) — 101 запись напрямую по
подстроке, включая явные ложные срабатывания вроде «Гонщик «Астаны» занял четвертое место»,
«astana_hub — Цифровой технопарк», спортивные/погодные/предвыборные новости. Ровно одна запись
защищена от удаления примером выше. Из оставшихся ~48 записей вручную проверены все — каждая
действительно о QazCloud (карточки в госреестре, профиль на Crunchbase, страница на 2GIS,
собственный сайт).

## Уведомления в Telegram

⚠ **Обновление (деплой на Vercel): индивидуальных уведомлений на каждое новое упоминание больше
нет.** Раньше отдельный бот слал в группу отдельное сообщение на каждое новое упоминание, через
свою очередь (`telegram-notify`) с rate-limit'ом, ретраями и «клеймом» от дублей — вся эта
инфраструктура удалена вместе с BullMQ (см. «Деплой на Vercel»). Единственный способ увидеть
находки в Telegram теперь — команда `/search` (см. «Закрытый пул ссылок: `/search` и `/status`»
выше): она читает упоминания закрытого пула ссылок за выбранный период прямо из БД (сборщиков не
запускает вообще). Эти упоминания и так уже лежат в БД (их туда кладёт отдельный скрипт ПРОМПТ 2,
не Telegram-бот) и видны на вкладке «Лента» в UI независимо от Telegram.

`TelegramNotifierService.formatMessage()` (форматирование одной карточки — заголовок, источник,
тональность, summary, фрагмент текста, дата, ссылка) в коде остался и покрыт тестами
(`telegram-notifier.service.spec.ts`), просто сейчас ничем не вызывается — `mentions.notification_sent`
в БД тоже остался (проставляется `true` для `is_backfill` находок), но ничего его больше не читает
для отправки.

- **Backfill за `BACKFILL_DAYS` дней (по умолчанию 60, т.е. ~2 месяца) — не про Telegram, актуально
  и сейчас.** Источник, у которого ещё не было ни одного успешного сбора
  (`sources.last_success_at IS NULL` — в том числе момент добавления нового источника), считается
  на этом вызове «историческим»: найденные материалы сохраняются как обычно, но помечаются
  `is_backfill = true`.
  - **Окно применяется best-effort.** Материал с известной датой публикации старше
    `BACKFILL_DAYS` дней пропускается (не сохраняется вообще, даже с пометкой backfill) —
    считается в отдельный счётчик `itemsSkippedOldBackfill`. Материал без определённой даты
    публикации (бывает у К-5 парсера, если на странице нет метатегов с датой) окном не
    ограничивается — глубже требуемого архива у источника физически может не быть, это не
    повод его отбрасывать.
  - **Значение настраивается через `.env`:** `BACKFILL_DAYS=60` — меняется без правки кода. В лог
    пишется сводка вида:

    ```
    Backfill (RSS): источник https://example.kz/rss — найдено 7 упоминани(й) за последние 60 дней
    (best-effort; пропущено как более старые: 3); уведомления по ним в Telegram не отправляются
    (is_backfill=true, notification_sent=true).
    ```

### К-2: глубокий проход поверх RSS (sitemap / пагинация К-5)

**Проблема.** RSS-лента у большинства сайтов отдаёт только последние N материалов (по диагностике
на реальных источниках проекта — от 10 до 200, обычно покрывает 1–6 дней), а не весь архив за
`BACKFILL_DAYS`. Упоминания, которые реально есть на сайте, но уже выпали из фида, раньше просто
не попадали в базу.

**Решение (`ParserService.deepCollect` + `fetchRssWithDeepScan`, `src/collectors/rss/rss-deep-scan.util.ts`).**
RSS остаётся быстрым каналом без изменений — сверху добавлен ещё один проход, который:
1. Пытается найти sitemap источника: сначала `Sitemap:` из `robots.txt` (приоритетно, это то, на что
   ссылается сам сайт), иначе — известные пути (`/sitemap.xml`, `/sitemap_index.xml`, `/wp-sitemap.xml`).
2. Если это sitemap-индекс, заходит в под-карты **начиная с самых свежих по `<lastmod>`** и
   останавливается, как только под-карта старше нужного окна — не тратит запросы на карты
   многолетней давности (проверено на matritca.kz — под-карты датированы вплоть до 2022 года).
   Если у индекса вообще нет `<lastmod>` (бывает — см. 365info.kz), берутся последние несколько
   под-карт как listed, без гарантии — это genuinely best-effort случай.
3. Если у источника нет sitemap вообще — резервный вариант: `crawlSite()` (К-5, обход
   листинга/пагинации, уже существовал в коде, но раньше нигде не вызывался).
4. Если не сработало ни то, ни другое (например, раздел новостей рендерится через JS и в HTML
   нет реальных `<a href>` на статьи — как на infozakon.kz/qaz.infozakon.kz) — источник не падает,
   в лог пишется явная причина, и просто продолжает работать быстрый канал (RSS).

**Окно и периодичность.** Первый в жизни источника глубокий проход (`sources.last_deep_scan_at IS
NULL` — это касается и совсем новых источников, и всех существующих на момент выхода этой
фичи) идёт на всю глубину `BACKFILL_DAYS`. Дальше — раз в `RSS_DEEP_SCAN_INTERVAL_HOURS` (по
умолчанию 24 часа) и только на `RSS_DEEP_SCAN_LOOKBACK_DAYS` назад (по умолчанию 7 дней) — этого
достаточно, чтобы подобрать то, что успело выпасть из RSS между двумя проходами, без пере-обхода
всего архива на каждый `/search`. Планировщика в проекте по-прежнему нет (см. «Деплой на
Vercel») — периодичность держится на `last_deep_scan_at`, а не на фоновом таймере: проверка
"пора ли" происходит на каждом вызове `/search`/«Добавить по ссылке», сам глубокий проход — только
когда действительно пора.

## Исправление: PARSER-источники не проходили глубокий обход

**Проблема.** Всё написанное выше про `deepCollect`/`crawlSite` — реальный работающий код, но до
этого исправления он был подключён только к RSS-источникам, через `fetchRssWithDeepScan`. Источник
без RSS-ленты вообще (тип `PARSER` — так автоопределяется, если у сайта не нашлось RSS/Atom-фида,
см. `source-detect.service.ts`) в обоих местах, где вообще что-либо собирается (тестовый сбор при
«Добавить по ссылке» и команда `/search` — фонового сбора по расписанию в проекте нет, см. «Деплой
на Vercel»), вызывал только `ParserService.fetchPage(source.url)` — одну загрузку самого URL
источника (обычно главной страницы), разобранную как **единственную статью**. Ни один настоящий
материал сайта никогда не читался. Именно поэтому упоминание компании, опубликованное на
`sknews.kz` (у него не нашлось RSS → тип PARSER), не могло быть найдено: бот ни разу не прочитал ни
одной статьи этого сайта.

**Решение (`fetchParserWithDeepScan`, `src/collectors/parser/parser-deep-scan.util.ts`).**
Симметричный аналог `fetchRssWithDeepScan` — тот же `ParserService.deepCollect()` (sitemap, либо
HTML-пагинация как fallback), то же троттлирование через `sources.last_deep_scan_at` и те же самые
переменные `RSS_DEEP_SCAN_INTERVAL_HOURS`/`RSS_DEEP_SCAN_LOOKBACK_DAYS` (см. выше — сознательно не
дублировались под PARSER-специфичные имена, это ровно тот же sitemap/HTML-проход). В отличие от
RSS, у PARSER-источника нет отдельного быстрого "фида", с которым можно было бы слить результат —
поэтому пока не подошло время для очередного глубокого прохода (`dueForDeepScan === false`),
функция просто возвращает пусто, а не подменяет это единственной страницей как раньше. И
`source-onboarding.service.ts` (`fetchByType`, case `PARSER`), и `on-demand-search.service.ts`
(канал `'Parser'`) переведены на эту функцию — голый `fetchPage()` для PARSER-источников больше не
вызывается ни там, ни там.

**Диагностика при добавлении источника.** `ParserService.deepCollect()` теперь возвращает не
просто массив, а `{ items, strategy }`, где `strategy` — `'sitemap' | 'html-pagination' | 'none'`
(к ним `fetchParserWithDeepScan` добавляет ещё `'skipped'`/`'error'` для случаев, когда сам
глубокий проход не запускался). При «Добавить по ссылке» это попадает в новое поле
`AddByLinkResult.deepScanNote` (форма на фронтенде показывает его под основным сообщением,
`import-sources.ts` — в скобках после строки `OK`), так что видно не только «источник подключён»,
но и «каким способом» — вместо того, чтобы для этого лезть в лог бэкенда.

**Бюджет времени.** Полноценный обход одного PARSER-источника — это потенциально десятки HTTP-
запросов подряд (по одному на статью), а `/search` выполняется синхронно в рамках одного запроса к
serverless-функции на Vercel Hobby (жёсткий потолок 60с) — см. «Бюджет времени `/search`» выше,
там же и разбор конкретно этого риска для PARSER-источников с реальными цифрами по sknews.kz.

**Проверка на живых данных (sknews.kz).** Полноценный `docker compose up` в этой среде недоступен
(нет запущенного Docker-демона) — проверка сделана прямым вызовом `ParserService.deepCollect()`
против `https://sknews.kz/` (ровно тот код, который использует `fetchParserWithDeepScan`):

- `robots.txt` реально указывает `Sitemap: https://sknews.kz/sitemap.xml` — `discoverSitemaps()`
  находит его. Но сам `sitemap.xml` в момент проверки отвечал **HTTP 500** — `deepCollect`
  корректно залогировал ошибку загрузки конкретного файла sitemap и откатился на резервный путь
  (не упал и не вернул старую однострочную "статью").
- Резервная HTML-пагинация (`crawlSite`) реально нашла и разобрала материалы с живого сайта: на
  окне `BACKFILL_DAYS=60` (параметры первого/онбордингового прохода) — **36 настоящих статей**
  (например «Казатомпром финансирует строительство современной больницы в Туркестанской области»,
  `https://sknews.kz/news/view/kazatomprom-finansiruet-stroitelystvo-sovremennoy-bolynicy-v-turkestanskoy-oblasti`)
  вместо нуля, за 45978мс — упёрлось ровно в дедлайн (45с), корректно остановившись на 36 из 60
  найденных ссылок вместо зависания до конца списка (лог: `crawlSite: бюджет времени исчерпан —
  останавливаю разбор материалов https://sknews.kz/, собрано 36 из 60`). Это подтверждает и сам
  фикс (реальные статьи читаются), и работу дедлайна на реальном медленном источнике.
- С параметрами конкретно `/search`-контекста (`PARSER_ONDEMAND_MAX_ARTICLES=15`,
  `PARSER_ONDEMAND_CRAWL_DELAY_MS=150`, `PARSER_ONDEMAND_SOURCE_BUDGET_MS=10000`) — обход
  корректно остановился на границе 10-секундного бюджета источника, собрав 6 из 15 запрошенных
  статей (**10160мс**), не тронув остальные каналы/источники общего `/search`-бюджета.
- ⚠ Честная оговорка, замеченная в реальном выводе: несколько ссылок с сайта (например
  `/news/category/...`) прошли ту же эвристику "похоже на статью" (`ARTICLE_PATH_HINT` совпадает и
  с `/news/category/...`, не только с `/news/view/...`) и попали в выдачу как заголовки категорий,
  а не отдельные материалы — это ограничение существовавшей раньше эвристики `looksLikeArticleUrl`
  (не новый код этого фикса), не блокирует задачу и не заведено отдельным тикетом здесь, но стоит
  знать при следующей доработке `extractArticleLinks`/`looksLikeArticleUrl`.
- Кнопка «Ещё новости» на сайте — действительно `<a href="javascript:;">`, без `rel="next"` и без
  текста «следующая/далее/next» — `findNextPageUrl()` её не распознаёт, ровно как и предполагалось
  в задаче. Раз sitemap у sknews.kz на момент проверки не работал, "глубина" обхода для него сейчас
  ограничена одной страницей листинга (но это уже реальные статьи, а не пусто, как было раньше). Если
  `sitemap.xml` у sknews.kz когда-нибудь заработает (это временная ошибка на стороне сайта, не
  постоянное отсутствие), обход автоматически станет глубже — код уже пробует sitemap первым при
  каждом проходе.

## Закрытый пул ссылок: `/search` и `/status` (ПРОМПТ 1 из 2)

**Это заменяет всё, что было написано в предыдущих версиях README про `/search`/`/status` —
опрос каналов, лимит 30 дней, бюджет времени, стоимость OpenAI web search. Ничего из этого больше
не относится к `/search`/`/status`** (соответствующие исторические разделы ниже помечены явно).

### Идея

Раньше `/search` был **сборщиком**: по нажатию кнопки периода бот последовательно опрашивал RSS,
Parser, Telegram-каналы, NewsAPI, VK и объединённый веб-поиск OpenAI прямо внутри одного HTTP-
запроса, ограниченного 60-секундным потолком Vercel Hobby — отсюда максимум периода в 30 дней и
собственный внутренний тайм-бюджет (`OnDemandSearchService`, теперь удалён).

Теперь `/search` — это **просмотрщик закрытого пула ссылок**. У проекта есть заранее собранный,
вручную провалидированный список ссылок на статьи (~169 URL на момент этого обновления, каждая
точно содержит упоминание компании) — сами ссылки читает, определяет дату публикации и тональность
**отдельный скрипт** (ПРОМПТ 2, не этот backend-процесс, запускается вручную/по расписанию вне
Vercel), результат сохраняется в таблицу `curated_links` + обычные `mentions` с проставленным
`curated_link_id`. `/search` и `/status` **только читают уже готовые записи из БД**
(`CuratedSearchService`, `backend/src/curated/curated-search.service.ts`) — ни сети, ни OpenAI, ни
обращения к `sources`/коллекторам, ни тайм-бюджета: единственная стоимость — обычный SQL-запрос.
Это же снимает старое ограничение периода в 30 дней — глубина архива теперь определяется только
тем, какие даты реально есть в пуле, а не 60-секундным потолком Vercel.

Код всех 6 каналов сбора (RSS/Parser/Telegram/NewsAPI/VK/OpenAI web search) не удалён — им
по-прежнему пользуется форма «Добавить по ссылке» (`SourceOnboardingService`) для разового
тестового сбора сразу после добавления источника. `OnDemandSearchService` (старая реализация
`/search`, опрашивавшая эти каналы) удалён полностью вместе с модулем `search-on-demand` — он
остался бы мёртвым кодом без единого вызывающего.

### Схема данных

Миграция `CuratedLinks1756400000000` (аддитивная, с рабочим `down()`):

- **`curated_links`** — реестр самого пула: `id`, `url`, `url_hash` (sha256 нормализованного URL,
  `UNIQUE` — это ключ дедупликации пула), `host`, `group_label`, `status` (`pending` |
  `processed` | `not_relevant` | `failed` | `excluded` — обычный `varchar`, не PG-enum: статусами
  управляет внешний скрипт ПРОМПТ 2, а не этот backend, и varchar не требует `ALTER TYPE` на
  каждый новый статус), `attempts`, `last_error`, `date_source` (`page` | `url` | `model` — как
  ПРОМПТ 2 определил дату), `mention_id`, `last_attempt_at`, `processed_at`, `created_at`,
  `updated_at`. **Никакой HTTP-контроллер эту таблицу не отдаёт** — `CuratedModule` сознательно
  без `@Controller`, единственный потребитель — `TelegramBotService` через `CuratedSearchService`.
- **`mentions.curated_link_id`** (`uuid`, nullable, partial `UNIQUE` — `WHERE curated_link_id IS
  NOT NULL`) — связывает обычную запись `mentions` с породившей её строкой `curated_links`.
  Партиальный (не обычный) уникальный индекс: у подавляющего большинства `mentions` (все находки
  остальных 6 каналов) это поле `NULL`, обычный `UNIQUE` разрешил бы только одну такую запись на
  всю таблицу.
- **`mentions.url_hidden`** (`boolean`, `DEFAULT false`) — «URL этой записи никогда не должен
  показываться» независимо от того, жива ли ещё её `curated_links`-запись: удаление строки
  `curated_links` (`ON DELETE SET NULL` на `mentions.curated_link_id`) не должно «проявлять» URL
  заново. Флаг существует отдельной колонкой именно поэтому.
- **`SourceKind.CURATED`** (`source_type_enum` += `'curated'`) — одна системная запись `sources`
  (`url = 'curated://internal'`, `name = 'Подборка материалов'`), заводится идемпотентно при
  каждом старте backend (`CuratedSourceBootstrapService.onModuleInit`, тот же паттерн
  `SourcesService.ensureSingleton`, что и у К-1/К-4). Её не опрашивает ни один канал — она нужна
  только чтобы у этого «источника» был обычный статус в разделе «Источники» на фронтенде.

Накатить на облачную БД (Neon/Supabase) — **вручную, сам не запускаю**:

```sh
cd backend
DATABASE_URL="postgres://user:pass@host/db?sslmode=require" npm run migration:run
```

### `CuratedSearchService` — контракт (расширяется ПРОМПТ 2)

```ts
search(periodDays, now = new Date())
  -> { periodDays, dateFrom, dateTo, total, bySentiment, undatedCount, pool }

findPage(periodDays, offset, limit, now?)
  -> CuratedMentionView[]  // id, title, sourceLabel, publishedAt, sentiment, summary, snippet

getPoolStats()
  -> { totalLinks, byStatus, mentionsTotal, undatedMentions, firstArticleDate, lastArticleDate, lastProcessedAt }
```

Запросы к `mentions` явно выбирают только нужные поля (`select([...])`) и **никогда** не выбирают
`url`/`reprints` — это гарантия на уровне SQL, а не только на уровне текста сообщения: URL этой
таблицы физически не попадает в память процесса, обрабатывающего `/search`. `summary`/`snippet` в
`CuratedMentionView` уже обрезаны сервисом (`~250`/`~200` символов) — форматтер (`curated-message.
util.ts`) просто выбирает `summary ?? snippet`, ничего не обрезая сам.

### Период считается по дате статьи, календарными границами в `SEARCH_TIMEZONE`

`(mentions.published_at AT TIME ZONE :tz)::date BETWEEN :dateFrom AND :dateTo` — **не** `found_at`,
**не** `COALESCE`, и **не** вычитание миллисекунд: `dateFrom`/`dateTo` — календарные даты
(`curated-date.util.ts` считает их через `Intl.DateTimeFormat` на реальных Y-M-D компонентах, а не
на разнице таймстампов), поэтому граница периода — это полночь в `SEARCH_TIMEZONE` (по умолчанию
`Asia/Almaty`, UTC+5 без перехода на летнее время), а не в UTC, и арифметика «N дней назад»
корректно проходит через границы месяца/года и високосный день без ручных поправок. `dateTo` —
всегда сегодня в этой таймзоне; статьи «из будущего» (например, `published_at` в будущем из-за
ошибки определения даты у ПРОМПТ 2) в выборку не попадают. Инъекция `now` — ради детерминированных
тестов (`curated-search.service.spec.ts`, `curated-date.util.spec.ts`).

Упоминания без `curated_link_id` (все находки остальных 6 каналов) в выборку `/search` не входят
никогда. Упоминания с `curated_link_id`, но без `published_at` (ПРОМПТ 2 не смог определить дату),
в выборку **по периоду** тоже не входят ни при каком периоде — но считаются отдельно
(`undatedCount`) и явно упоминаются в сообщении, а не тихо исчезают.

### `SEARCH_PERIOD_DAYS` — список периодов вместо жёстко зашитых 5/9 кнопок

`.env`: `SEARCH_PERIOD_DAYS=1,3,7,14,30,90,180,365,730` (значение по умолчанию, если переменная не
задана или некорректна). Валидация (`curated/search-period.util.ts`): целые положительные числа,
без повторов, строго по возрастанию, каждое ≤3650 — при нарушении используется дефолт и пишется
`warn` в логах (не падение). Подписи (русские склонения) заданы вручную для «круглых» значений
(1 «Сутки», 3 «3 дня», 7 «Неделя», 14 «Две недели», 30 «Месяц», 90 «3 месяца», 180 «Полгода»,
365 «Год», 730 «2 года»); любое другое N получает подпись «N дн.». Кнопки — по 3 в ряд,
`callback_data = search_period:<days>`; нажатие кнопки со значением, отсутствующим в текущем
`SEARCH_PERIOD_DAYS` (устаревшая клавиатура из старого сообщения после смены `.env`), отвечает
`answerCbQuery('Неизвестный период')`, а не падает.

### Сообщение бота

1. `/search` → `«За какой период показать упоминания из пула ссылок?»` + кнопки периода.
2. Нажатие кнопки: `answerCbQuery()`, `editMessageText('Период: <подпись> (с dd.mm.yyyy по
   dd.mm.yyyy)')`, затем шапка и первая страница результатов — всё внутри одного `await`-цикла
   обработчика (см. «Почему обработчики бота дожидаются всего синхронно» выше).
3. **Шапка** (HTML): `<b>Упоминания за <подпись></b> (с … по …)`, строка
   `Всего: N · 🟢 a · 🔴 b · 🟡 c · ⚪ d`; при `undatedCount > 0` — отдельная строка «Без даты
   публикации (в выборки по периоду не входят): U»; если в пуле есть ссылки со статусом `pending`
   или `failed` — строка «В очереди на обработку: Q · с ошибкой: F».
4. **Каждая находка**: `<номер>. <эмодзи+подпись тональности> · <заголовок>` (обрезан до ~200
   символов), следующей строкой `<sourceLabel> · dd.mm.yyyy` (дата — в `SEARCH_TIMEZONE`), затем
   пересказ (`mentions.summary`, до ~250 символов, либо первые ~200 символов текста, если summary
   ещё нет). Весь текст экранирован (`escapeHtml`).
5. **Пагинация без ограничения по числу находок.** Одна «страница» — столько находок, сколько
   влезает в `SEARCH_MESSAGE_CHAR_LIMIT` (по умолчанию 3500 символов, жадная упаковка — минимум
   одна находка всегда показывается, даже если она сама по себе больше лимита); остаток — кнопка
   «Показать ещё (осталось N)» с `callback_data = search_more:<days>:<offset>` (`offset` — индекс
   первой ещё не показанной находки, сквозной по всему периоду, не «с начала текущей страницы»).
   Нажатие: проверка авторизации чата и валидности `days`/`offset`, `answerCbQuery()`, снятие
   клавиатуры с предыдущего сообщения (`editMessageReplyMarkup({inline_keyboard: []})`, best-effort
   — если сообщение уже нельзя редактировать, следующая страница всё равно отправляется), затем
   следующая страница отдельным сообщением (с новой кнопкой, если остались ещё находки). Между
   сообщениями внутри одного вызова паузы нет — Telegram-лимит на частоту сообщений здесь не
   актуален (одно сообщение на одно нажатие кнопки пользователем).
6. **Пустой результат:** если в пуле вообще нет ссылок или ещё ни одна не обработана —
   «Пул ссылок пуст или ещё не обработан.» Иначе, если для периода просто нет находок — «За
   <подпись> упоминаний в пуле ссылок не найдено. Обработано ссылок: P, самая свежая статья —
   dd.mm.yyyy.» (дата опускается, если во всём пуле ещё нет ни одной датированной статьи).
7. **Ошибка** (сбой БД и т.п.) — понятный текст с причиной (`error.message`, без стектрейса, без
   URL), бот никогда не молчит — ни при первом сообщении, ни при «Показать ещё».

### Приватность: бот нигде не показывает URL

Ни у одной находки, ни в шапке, ни в тексте ошибки — ни один код-путь `/search`/`/status` не имеет
доступа к `mentions.url`/`mentions.reprints` (`CuratedSearchService` их даже не выбирает из БД, см.
выше), поэтому утечка URL структурно невозможна, а не просто «не выведена в шаблоне». Тест на этот
инвариант (`curated-message.util.spec.ts`, `telegram-bot.service.spec.ts`) проверяет отсутствие
подстроки `http` в итоговом тексте каждого типа сообщения.

### `/status` — статистика пула вместо статуса по каналам

Раньше `/status` показывал `settings.collection_enabled` и последний успешный сбор по каждому
каналу. Теперь — статистика пула (`CuratedSearchService.getPoolStats()`, `curated-message.util.
buildStatusText`): всего ссылок; разбивка по статусам (обработано/не релевантны/с ошибкой/в
очереди); упоминаний в пуле; диапазон дат статей (самая ранняя — самая свежая); без даты; время
последней обработки (`MAX(curated_links.processed_at)`). Никаких URL, никакого чтения `sources`
для каналов сбора (`settings.collection_enabled` для `/status` больше не проверяется — эта
настройка управляла фоновым автосбором, которого нет уже с прошлого этапа, см. «Деплой на
Vercel»; авторизация чата — та же самая проверка, что и раньше.

### Переменные окружения

```
SEARCH_PERIOD_DAYS=1,3,7,14,30,90,180,365,730   # список периодов, см. валидацию выше
SEARCH_TIMEZONE=Asia/Almaty                      # календарные границы периода и отображение дат
SEARCH_MESSAGE_CHAR_LIMIT=3500                   # жадная упаковка находок в одну "страницу"
```

Устаревшие/удалённые (были нужны только `OnDemandSearchService`, который удалён): `SEARCH_TIME_
BUDGET_MS`, `SEARCH_DEEP_SCAN_PHASE_BUDGET_MS`, `PARSER_ONDEMAND_SOURCE_BUDGET_MS`,
`PARSER_ONDEMAND_MAX_ARTICLES`, `PARSER_ONDEMAND_CRAWL_DELAY_MS` — если они остались в `.env`,
можно удалить, ничего их больше не читает (см. `.env.example`, там оставлены закомментированными
как история). `PARSER_ONBOARDING_SOURCE_BUDGET_MS` **не удалён** — им по-прежнему пользуется
«Добавить по ссылке».

### Проверка на живых данных (локальный `docker compose`)

Прогнано на поднятом `docker compose up -d postgres` + миграциях + реальном `TelegramBotService.
handleUpdate()` (Telegram API замокан на уровне HTTP-клиента `Telegraf`, БД — настоящая):

- **6 тестовых упоминаний** (`example.com`, домен `test-curated-seed` в `curated_links.host` для
  прицельной очистки) с датами сегодня−2 дня / −20 дней / −5 месяцев / −14 месяцев / −3 года и
  одно без даты, разные тональности (`positive`/`negative`/`neutral`/`undefined`), часть с длинными
  (>250 символов) пересказами — проверить обрезку. Плюс по одной ссылке в статусах `pending` и
  `failed` — проверить строку «В очереди на обработку».
- **Период = Сутки (1д):** ни одно из 6 упоминаний не попало в окно (все старше суток) →
  «За Сутки упоминаний в пуле ссылок не найдено. Обработано ссылок: 6, самая свежая статья —
  18.09.2026.» — именно тот тестовый текст, что и ожидался, включая корректную «самую свежую» дату.
- **Период = Месяц (30д):** 2 из 6 (−2 дня, −20 дней) — шапка `Всего: 2 · 🟢 1 · 🔴 1 · 🟡 0 · ⚪ 0`,
  строка «Без даты публикации: 1», строка «В очереди на обработку: 1 · с ошибкой: 1»; длинный
  пересказ (>250 символов) корректно обрезан с «…».
- **Период = Год (365д):** 3 из 6 (добавляется −5 месяцев); **Период = 2 года (730д):** 4 из 6
  (добавляется −14 месяцев) — статья −3 года корректно **не** попала даже в 730-дневное окно
  (2 года < 3 лет), подтверждая, что окно считается календарно, а не «показать вообще всё, что
  есть».
- **Пагинация на 70 тестовых строках** (даты с шагом в 1 час за последние ~3 суток, домен
  `test-curated-pagination`): период «3 месяца» (90д) дал `Всего: 72` (70 новых + 2 из первой
  партии, попавшие в то же окно), разбитых на **6 страниц** по `search_more` (13 → 14 → 14 → 14 →
  14 → 3 находки на страницу, каждая ≤3434 символов при лимите 3500), с корректно уменьшающимся
  «осталось N» (59→45→31→17→3→кнопка исчезает на последней странице) и сквозным `offset`
  (13→27→41→55→69), без единого дубликата или пропуска находки между страницами.
- Все тестовые строки удалены после проверки (`DELETE ... WHERE host IN ('test-curated-seed',
  'test-curated-pagination')` — только строки, созданные для этой проверки).
- `docker compose up --build` (postgres + migrate + backend + frontend) поднимается целиком без
  ошибок; `GET /sources` показывает системный источник `curated://internal` с корректным именем;
  прямого HTTP-эндпоинта на `curated_links` не существует (`404` на любой такой путь) — приватность
  пула подтверждена не только на уровне кода бота, но и на уровне реального HTTP API.
- `docker build -f Dockerfile .` (см. примечание про имя файла в «Деплой на Vercel») собирается
  без ошибок с новым кодом.

## Наполнение пула: импорт, чтение страниц, дата, тональность (ПРОМПТ 2 из 2)

ПРОМПТ 1 (раздел выше) сделал **чтение** пула: `/search` и `/status` читают готовые записи из БД.
Этот раздел — про **запись**: как ссылки попадают в `curated_links` и как из них получаются
упоминания с датой, фрагментом и тональностью.

Всё управление пулом — **только CLI-скрипты**. HTTP-эндпоинта, отдающего `curated_links`, не
существует и не должно появиться (`CuratedModule` сознательно без `@Controller`).

### Файл со ссылками

Лежит в **`backend/data/curated-links.txt`** и **никогда не коммитится**: каталог `backend/data/`
добавлен в `.gitignore`, `.dockerignore`, `backend/.dockerignore` и `.vercelignore`. Проверить:

```sh
git check-ignore -v backend/data/curated-links.txt   # должен вывести правило из .gitignore
```

Формат — самый простой, какой можно править руками:

```
Tech                       <- непустая строка не с http(s):// — заголовок группы
https://site.example/a     <- ...и действует на все URL до следующего заголовка
https://site.example/b

bluescreen
https://other.example/x
```

Пустые строки игнорируются, пробелы по краям обрезаются (в реальном файле они есть). Дубли внутри
файла считаются, а не роняют импорт. URL до первого заголовка получает `group_label = NULL`.

**`group_label` — это то, что бот показывает как источник** вместо домена: читатель `/search`
видит «kursiv», а не адрес статьи.

### Нормализация URL и идентичность ссылки

`backend/src/curated/curated-url.util.ts`, `url_hash = sha256(нормализованный URL)`:

- хост — в нижний регистр, **путь — нет** (у profit.kz слаги в смешанном регистре, в нижнем они 404);
- `#fragment` и `utm_*` отбрасываются;
- **query-string сохраняется** — у ekaraganda.kz статьи живут по `/?mod=news_read&id=…`, и без
  query все пять её ссылок схлопнулись бы в одну;
- завершающий слэш убирается, только если путь длиннее `/`.

### Импорт

```sh
cd backend
npm run curated:import                     # по умолчанию backend/data/curated-links.txt
npm run curated:import -- путь/к/файлу.txt
```

Идемпотентно (`ON CONFLICT (url_hash) DO NOTHING`): повторный запуск после дописывания строк в файл
добавит только новые, уже обработанные ссылки не тронет. Домены из `EXCLUDED_DOMAINS` заводятся со
статусом `excluded` и **никогда не обрабатываются** (записываются, а не молча выбрасываются — чтобы
`curated:status` мог объяснить разницу между числом строк в файле и числом рабочих ссылок).

Скрипт печатает **только счётчики** — ни одного URL. Некорректная строка сообщается номером строки,
без её содержимого.

### Обработка ссылок

```sh
npm run curated:process                            # все pending
npm run curated:process -- --limit 10              # только первые N
npm run curated:process -- --concurrency 2
npm run curated:process -- --hosts sknews.kz,sk.kz # только эти сайты
npm run curated:process -- --force                 # перечитать уже обработанные
npm run curated:process -- --retry-failed          # вернуть к жизни failed
```

Что происходит с одной ссылкой (`CuratedIngestService.processLink`):

1. **Чтение страницы.** `CURATED_READ_MODE=auto` (по умолчанию): сначала бесплатный HTTP-парсер
   (`ParserService.fetchPageDetailed`). Если страница не скачалась, пустая или текст короче
   `CURATED_MIN_PAGE_TEXT_CHARS` (≈ анти-бот или JS-рендер) — **платный** fallback через OpenAI
   Responses API с инструментом `web_search`, жёстко ограниченным одним доменом
   (`filters.allowed_domains: [host]`, `tool_choice`), моделью `OPENAI_SOCIAL_SEARCH_MODEL`,
   `reasoning: low` и strict `json_schema`. Режим `openai` — всегда через OpenAI. Работает
   **независимо** от `SOCIAL_SEARCH_ENABLED` (тот флаг выключает К-6 как канал сбора, а не это).
   Перед платным fallback делается ещё одна бесплатная попытка с завершающим слэшем: sk.kz отдаёт
   404 на путь без него и 200 — с ним.
2. **Дата статьи.** Порядок: метаданные страницы → дата из URL → ответ модели → `null`. Источник
   записывается в `curated_links.date_source`. Дата вне `2000-01-01…завтра` считается недостоверной
   и не принимается — берётся следующий источник. **Текущая дата не подставляется никогда**: статья
   без даты остаётся без даты и считается отдельно («Без даты» в `/status`), потому что неверная
   дата попала бы в каждый период `/search` навсегда.
3. **Релевантность.** Тот же `ActiveKeywordSet`, что и у остальных каналов, но **без минус-слов**:
   они настраивались против шума каналов, которые ищут по всему вебу, а каждая ссылка пула уже
   отобрана человеком — минус-слово здесь не фильтрует шум, а выбрасывает намеренно добавленную
   ссылку (минус-слово «Астан» отвергало настоящую статью про дата-центр под Астаной). Нет
   упоминания — статус `not_relevant`, упоминание не создаётся, причина в `last_error`.
4. **Контекст.** Чистая функция `buildMentionContext`: заголовок + фрагменты вокруг вхождений
   названия компании (±600 символов, пересекающиеся сливаются, всего до 4000). Без этого в длинном
   обзоре с одним упоминанием классификатор увидел бы только первые 6000 символов, где компании
   может вообще не быть.
5. **Тональность.** Существующий `SentimentAnalysisService.classify(title, fragment)` **без URL**
   (иначе он перекачал бы страницу и потерял выбранный фрагмент). Второго промпта тональности не
   заводится. Нет ключа или ошибка OpenAI — упоминание создаётся с тональностью «не определена».
6. **Итог.** `processed` + `mention_id` + `processed_at` + `date_source`, либо `attempts + 1` и
   человекочитаемый `last_error`. После `CURATED_MAX_ATTEMPTS` попыток — `failed`.

Одна упавшая ссылка **не останавливает** остальные. На ссылку целиком — таймаут
`CURATED_LINK_TIMEOUT_MS` через `AbortController`. К одному хосту — **строго один запрос за раз**
с паузой `CURATED_HOST_DELAY_MS` (у sknews.kz 49 ссылок подряд — иначе это выглядит как скрейп и
кончается баном); общий параллелизм по разным хостам — `CURATED_CONCURRENCY`.

Уже `processed` ссылки повторно не читаются (каждое чтение через OpenAI платное) — кроме `--force`.
`--force` **обновляет** уже созданное упоминание, а не вставляет второе: вставки пула идут со
`skipDedup`, а partial `UNIQUE` по `curated_link_id` погасил бы вторую строку, и исправление
(например, в извлечении даты) не доехало бы до существующей записи.

### Состояние пула

```sh
npm run curated:status                      # счётчики по статусам и по группам
npm run curated:status -- --show-problems   # + список failed/not_relevant со ссылками
```

`--show-problems` — **единственное** место, где URL пула вообще печатается, и только в терминал
оператора: чтобы проблемную ссылку можно было открыть и починить. В файлы, логи и коммиты она не
попадает.

### Ленивая дообработка внутри `/search`

При `CURATED_LAZY_PROCESS=true` перед чтением из БД `/search` дообрабатывает до
`CURATED_LAZY_MAX_LINKS` ссылок в пределах `CURATED_LAZY_BUDGET_MS`, не начиная новых после
дедлайна. Ссылка, у которой дата видна прямо в URL и старше запрошенного периода, пропускается: она
всё равно не попадёт в эту выдачу, а чтение стоит денег. Любая ошибка этого шага **гасится** —
чтение из БД не должно ломаться из-за дообработки. По умолчанию выключено: обработчик бота должен
укладываться в ~30 с.

### Приватность

Авторизации у API нет: всё, что сериализует backend, доступно любому, кто знает адрес деплоя.
Поэтому скрытие ссылок сделано **на сервере**, а не через CSS или условный рендер во фронтенде.

1. Ссылки лежат **только** в `curated_links`, не в `sources`. Эндпоинтов, отдающих эту таблицу, нет.
2. Для упоминаний с `url_hidden = true` наружу не уходят ни `url`, ни `reprints` — централизованно,
   глобальным `MentionPrivacyInterceptor` (`APP_INTERCEPTOR` в `AppModule`), а не точечно в каждом
   контроллере: новый эндпоинт, отдающий упоминания, защищён в день, когда его написали.
3. **Из `text`/`summary`/`title` таких упоминаний вырезаются любые http(s)-ссылки.** Это не
   гигиена, а необходимость: новостные страницы печатают собственный адрес в теле статьи (блок
   «скопировать ссылку», шеринг) — на kz.kursiv.media это дало реальную утечку, найденную
   `curated:leak-check` на живом стенде: `url` скрывался корректно, а тот же адрес уезжал в `text`.
   Ссылки вырезаются и при сборе контекста (в БД они не попадают), и на выдаче.
4. `source_label` таких упоминаний — `group_label` из файла (Tech, bluescreen, kursiv…), не домен
   и не URL.
5. Дедупликация: вставки пула идут со `skipDedup: true`, а обычные вставки **игнорируют строки с
   `url_hidden = true`** в обеих проверках (по хэшу и по схожести текста). Иначе при слиянии
   «перепечаток» скрытый URL попал бы в `reprints` открытого упоминания — или наоборот.
6. Логи приложения и скриптов содержат только id ссылки и хост (`curatedLinkRef`), полный URL —
   никогда; `last_error` тоже чистится от URL.
7. `CURATED_LINKS_EXPOSE_URLS=true` отключает скрытие **только для REST API и фронтенда**.
   На Telegram-бота не влияет: он ссылки не показывает никогда и колонку `url` даже не выбирает.
8. Фронтенд: `Mention.url: string | null`. Если ссылки нет, `MentionCard` показывает заголовок
   обычным текстом, без `<a>`. Раздел «Источники» показывает только системную запись
   `curated://internal` с числом упоминаний, без псевдо-URL.

### Извлечение даты: что пришлось чинить на реальных сайтах

Дата — основа всей фичи (бот отбирает по периодам), поэтому здесь два неочевидных места:

- **Дата статьи, а не первая дата на странице.** Старый `extractPublishedAt` брал
  `$('time[datetime]').first()`. На любом сайте с сайдбаром «последние новости» это **сегодняшняя**
  дата: на ekaraganda.kz все пять статей пула получили сегодняшнее число и попали бы в каждый
  период `/search` навсегда. `fetchPageDetailed` теперь читает meta-теги, затем JSON-LD
  (`schema.org` `datePublished`), затем `<time>` **ближайший к `<h1>`** — расширяя область поиска
  от заголовка наружу, а не сверху вниз по документу. Сайдбар живёт в другом поддереве и в эту
  область не попадает.
- **Дата прописью.** Многие казахстанские сайты не публикуют машиночитаемую дату вообще — ни
  `article:published_time`, ни JSON-LD, ни `<time datetime>` (sknews.kz, profit.kz, infozakon.kz,
  rail-news.kz — 81 из 169 ссылок пула). `common/human-date.util.ts` читает «20 января 2023»,
  «22 қыркүйек 2026», «28.10.2024». Если рядом с заголовком даты нет, страница сканируется целиком —
  но результат принимается, **только если на всей странице названа ровно одна дата**
  (`findUnambiguousDate`): страница с сайдбаром даёт несколько дат и честно возвращает `null`,
  вместо того чтобы проставить сегодняшнюю.

Итог на реальном пуле: доля статей с датой выросла с **46% до 99%** (166 из 167) — и всё это
бесплатным HTTP-парсером, без единого платного вызова OpenAI.

### Проверка на живом окружении

Прогнано на локальной БД `docker compose` (`DB_HOST -> 127.0.0.1:5432/mentions`; `DATABASE_URL` в
этом окружении не задан, поэтому облачная БД не затрагивалась — для неё команды выше).

- Импорт: 220 строк файла → 171 строка с URL → **169 уникальных**, 2 дубля внутри файла,
  20 групп, 0 некорректных URL.
- Полный прогон 169 ссылок: **167 `processed`, 2 `not_relevant`, 0 `failed`, 0 `pending`**;
  все 169 прочитаны бесплатным HTTP-парсером, **0 вызовов `web_search`**.
- Обе `not_relevant` проверены вручную и признаны верными: страница анонса воркшопа на
  astanahub.com и статья про threat hunting на bluescreen.kz действительно не содержат названия
  компании ни в одном написании.
- Даты: **166 из 167** (99%). Две ссылки остались без даты, из них одна исправлена
  (`findUnambiguousDate`), у последней (itsx.kz) даты нет на странице вообще ни в каком виде.
- `/search` по периодам: 1/7/30 дней — 0 (самая свежая статья пула от 18.08.2026), 365 — 36,
  730 — 63, 3650 — 166; «без даты» — 1, в периоды не входит. Диапазон дат пула 01.06.2018 —
  18.08.2026.
- `npm run curated:leak-check` против поднятого стенда: **0 совпадений** по 169 ссылкам в 4
  ответах (`/mentions`, `/mentions/stats`, `/sources`, текст бота).
- **Тональность не проверена на живых данных: `OPENAI_API_KEY` в этом окружении пуст**, поэтому все
  167 упоминаний имеют тональность «не определена», а платный путь чтения страниц (fallback на
  OpenAI) ни разу не выполнялся. Когда ключ появится, достаточно
  `npm run curated:process -- --force` — он доклассифицирует записи, оставшиеся без тональности,
  не трогая уже определённые и не вставляя дублей.

## Дедупликация перепечаток

При вставке нового материала:
1. Сначала проверяется точное совпадение по хэшу заголовка+текста (как на прошлом этапе).
2. Если хэш не совпал, ищется близкий по заголовку материал через `pg_trgm`
   (`similarity(title, ...) > 0.6`) в окне ±5 дней по дате публикации.

В обоих случаях новая строка не создаётся — ссылка на источник-перепечатку добавляется в
поле `reprints` (jsonb) существующей карточки упоминания.

**Исключение: К-6 (веб-поиск).** Для `source_type = 'social_search'` оба этих шага полностью
отключены (`skipDedup: true`) — см. раздел «К-6» выше, почему находки из веб-поиска намеренно не
объединяются между собой, даже когда текст похож.
